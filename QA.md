## Владение, заимствование, лайфтаймы

### 1. Что такое владение в Rust и какие у него три правила

Владение это модель управления памятью, в которой у каждого значения в любой момент времени есть ровно один владелец. Когда владелец выходит из области видимости, значение освобождается. Три правила формулируются так. У каждого значения есть владелец. В один момент времени у значения только один владелец. Когда владелец уходит из скоупа, вызывается drop и память освобождается.

Эта модель заменяет ручное управление памятью и сборщик мусора одновременно. Компилятор знает, где значение перестает быть нужным, и вставляет освобождение сам. Никаких рантайм проверок при этом не происходит.

```rust
fn main() {
    let s = String::from("hello"); // s владеет буфером
    take(s);                        // владение передано в take
    // println!("{}", s);          // ошибка компиляции, s больше не валиден
}

fn take(s: String) {
    println!("{}", s);
} // здесь s уходит из скоупа, буфер освобождается
```

Важно в этом примере то, что компилятор отслеживает передачу владения статически. Если раскомментировать println после take, код просто не соберется.

### 2. Чем move отличается от copy и какие типы реализуют Copy

Для типов, не реализующих Copy, присваивание и передача в функцию это move. Старая переменная становится невалидной. Для типов с Copy при тех же операциях делается побитовая копия, обе переменные остаются валидными. Copy могут реализовывать только типы, у которых нет ресурсов с деструктором. Это все примитивы, кортежи и массивы из Copy типов, ссылки &T, сырые указатели, функции и замыкания без захвата.

String, Vec, Box, HashMap, любой тип с Drop не могут быть Copy. Это сделано специально, чтобы не было двойного освобождения.

```rust
fn main() {
    let a: i32 = 10;
    let b = a;           // copy, a остается валидным
    println!("{} {}", a, b);

    let s = String::from("x");
    let t = s;           // move, s больше нельзя использовать
    println!("{}", t);
}
```

Ключ в том, что Copy это маркерный трейт без методов. Компилятор смотрит на его наличие и выбирает семантику присваивания.

### 3. Разница между &T и &mut T, какие правила заимствования действуют одновременно

&T это разделяемая ссылка, через нее нельзя менять значение. &mut T это эксклюзивная ссылка, через нее можно менять. Правило одно и простое. В один момент времени для одного значения может существовать либо любое число &T, либо ровно одна &mut T. Совмещать нельзя.

Это правило проверяется заёмщиком (borrow checker) на этапе компиляции. Оно дает гарантию отсутствия гонок данных в безопасном Rust и позволяет компилятору агрессивно оптимизировать, потому что он знает, что через &T значение не изменится.

```rust
fn main() {
    let mut v = vec![1, 2, 3];
    let r1 = &v;
    let r2 = &v;
    println!("{:?} {:?}", r1, r2); // две shared ссылки одновременно нормально

    let m = &mut v;
    m.push(4);                      // эксклюзивная ссылка, других нет
}
```

Если попытаться взять &mut v, пока r1 и r2 еще используются, компилятор откажется собирать. Срок жизни ссылок при этом считается до последнего использования, а не до конца блока, благодаря NLL.

### 4. Что такое лайфтайм и зачем нужны явные аннотации

Лайфтайм это область кода, в течение которой ссылка валидна. Компилятор всегда знает лайфтайм каждой ссылки, но иногда не может вывести связи между несколькими ссылками сам. Тогда программист пишет аннотации, чтобы рассказать компилятору, что ссылки связаны.

Аннотация ничего не меняет в рантайме. Это контракт. Запись fn f<'a>(x: &'a str, y: &'a str) -> &'a str говорит, что возвращаемая ссылка живет не дольше, чем самый короткий из лайфтаймов x и y.

```rust
fn longest<'a>(a: &'a str, b: &'a str) -> &'a str {
    if a.len() > b.len() { a } else { b }
}

fn main() {
    let s1 = String::from("long string");
    let result;
    {
        let s2 = String::from("short");
        result = longest(&s1, &s2);
        println!("{}", result); // ок, s2 еще жив
    }
    // println!("{}", result); // ошибка, result привязан к лайфтайму s2
}
```

Главное здесь, что компилятор отказывается выпустить ссылку наружу за пределы валидности данных.

### 5. Правила elision лайфтаймов

Правил три. Первое. Каждому входному параметру со ссылкой назначается свой лайфтайм. Второе. Если у функции один входной лайфтайм, он автоматически становится лайфтаймом всех выходных ссылок. Третье. Если среди входов есть &self или &mut self, лайфтайм self становится лайфтаймом выходов.

Эти правила покрывают подавляющее большинство случаев и позволяют не писать аннотации руками. Когда правил не хватает, компилятор просит явных аннотаций.

```rust
struct Parser<'s> { input: &'s str }

impl<'s> Parser<'s> {
    fn rest(&self) -> &str { self.input } // лайфтайм выводится из &self
}

fn first_word(s: &str) -> &str {          // лайфтайм единственный, elision работает
    s.split_whitespace().next().unwrap_or("")
}
```

В методе rest возвращаемая ссылка живет, пока жива сама структура.

### 6. Что такое 'static и почему это два разных смысла

'static как лайфтайм ссылки означает, что данные живут все время работы программы. Все строковые литералы имеют тип &'static str, потому что лежат в секции данных бинарника. 'static как бOund в дженериках, T: 'static, означает другое. Тип T не содержит ссылок с лайфтаймом короче 'static. Иначе говоря, T не зависит от заимствованных данных. Owned типы (String, Vec, i32, Box<T> где T: 'static) удовлетворяют T: 'static, потому что внутри нет коротких ссылок.

```rust
fn store<T: 'static + Send>(x: T) {
    std::thread::spawn(move || drop(x));
}

fn main() {
    store(String::from("ok"));
    let s = String::from("hi");
    store(s);                  // ок, String владеет своими данными
    // let r: &str = &s;
    // store(r);              // ошибка, &str с коротким лайфтаймом
}
```

Ограничение 'static в spawn нужно потому, что поток может пережить вызывающий стек.

### 7. Что такое NLL и как работает borrow checker сейчас

NLL это non lexical lifetimes. До 2018 года лайфтайм ссылки считался от точки создания до конца лексического блока. Это давало много ложных срабатываний. С NLL лайфтайм считается до последнего реального использования. Дальше анализ перешел на полноценный поток управления, MIR borrow check. Чекер строит граф использований и проверяет правила алиасинга по нему.

```rust
fn main() {
    let mut v = vec![1, 2, 3];
    let r = &v[0];
    println!("{}", r);   // последнее использование r здесь
    v.push(4);            // ок, заимствование уже закончилось
}
```

До NLL такой код не компилировался, потому что r формально жил до конца main.

### 8. Что делает Box и когда он нужен

Box<T> это владеющий указатель на значение в куче. Сам Box лежит на стеке и при дропе освобождает кучу. Нужен в трех типичных случаях. Когда размер типа неизвестен на этапе компиляции, например рекурсивные типы. Когда нужно передать большое значение, не копируя его. Когда нужен trait object Box<dyn Trait> для динамической диспетчеризации с владением.

```rust
enum List { Cons(i32, Box<List>), Nil }

fn handler() -> Box<dyn Fn(i32) -> i32> {
    Box::new(|x| x + 1)
}

fn main() {
    let list = List::Cons(1, Box::new(List::Cons(2, Box::new(List::Nil))));
    let _ = list;
    let f = handler();
    println!("{}", f(10));
}
```

Без Box рекурсивный enum имел бы бесконечный размер и не компилировался.

### 9. Rc и Arc, в чем разница и когда что выбирать

Rc<T> и Arc<T> это умные указатели с подсчетом ссылок. Rc для одного потока, счетчик внутри обычный. Arc для нескольких потоков, счетчик атомарный. Atomic операции дороже, поэтому Arc используют только когда данные пересекают границу потоков. Оба дают только разделяемый доступ. Чтобы менять данные внутри, нужна интишняя мутабельность через RefCell для Rc или Mutex/RwLock для Arc.

```rust
use std::sync::Arc;
use std::thread;

fn main() {
    let data = Arc::new(vec![1, 2, 3]);
    let mut handles = vec![];
    for _ in 0..3 {
        let d = Arc::clone(&data);
        handles.push(thread::spawn(move || println!("{:?}", d)));
    }
    for h in handles { h.join().unwrap(); }
}
```

Arc::clone тут не копирует вектор, только увеличивает счетчик. После последнего drop вектор освобождается.

### 10. Что такое interior mutability и какие типы ее реализуют

Интерьорная мутабельность это способность менять значение через разделяемую ссылку. На уровне типов это контролируется UnsafeCell, на нем построены Cell, RefCell, Mutex, RwLock, atomic типы. Cell дает дешевую замену значения целиком без проверок. RefCell проверяет правила заимствования в рантайме и паникует при нарушении. Mutex и RwLock делают то же самое для многопоточности и блокируют поток.

```rust
use std::cell::RefCell;

fn main() {
    let counter = RefCell::new(0);
    *counter.borrow_mut() += 1;
    *counter.borrow_mut() += 1;
    println!("{}", counter.borrow()); // 2
}
```

Интересный момент. Если одновременно взять borrow и borrow_mut, программа упадет в рантайме. Это плата за гибкость.

### 11. Что такое Cow и где он реально полезен

Cow это перечисление с двумя вариантами, Borrowed и Owned. Используется, когда чаще всего данные только читаются, но иногда их нужно изменить. Тогда можно не аллоцировать заранее. Типичный пример это нормализация строк, замена символов, escape для URL. Если ничего менять не надо, возвращаем заимствованную ссылку. Если надо, аллоцируем String и возвращаем Owned.

```rust
use std::borrow::Cow;

fn escape(s: &str) -> Cow<str> {
    if s.contains('&') {
        Cow::Owned(s.replace('&', "&amp;"))
    } else {
        Cow::Borrowed(s)
    }
}

fn main() {
    let a = escape("hello");
    let b = escape("a & b");
    println!("{} | {}", a, b);
}
```

Для строки без амперсанда аллокации не будет вовсе. Это и есть выигрыш.

### 12. Что такое Drop и можно ли вызвать его руками

Drop это трейт с методом drop, который компилятор вызывает автоматически при выходе значения из скоупа. Внутри обычно освобождают ресурсы. Файлы, сокеты, мьютексы, буферы. Руками вызвать Drop::drop нельзя, компилятор это запрещает, чтобы не было двойного освобождения. Если нужно освободить раньше времени, есть свободная функция std::mem::drop, которая просто принимает значение по владению и роняет его в конце.

```rust
struct Guard(&'static str);

impl Drop for Guard {
    fn drop(&mut self) { println!("drop {}", self.0); }
}

fn main() {
    let g = Guard("a");
    drop(g);             // освобождаем сразу
    println!("после drop");
}
```

Порядок дропа полей в структуре определен. Сначала структура целиком, потом ее поля в порядке объявления.

### 13. Что такое самоссылочная структура и почему ее сложно делать

Структура, в которой одно поле ссылается на другое, считается самоссылочной. Проблема в том, что Rust по умолчанию свободно перемещает значения. После перемещения внутренняя ссылка стала бы висячей. Поэтому такие структуры либо строятся через Pin и unsafe, либо избегаются. На уровне приложения почти всегда лучше переформулировать задачу через индексы, через Rc или через арены.

```rust
use std::pin::Pin;
use std::marker::PhantomPinned;

struct SelfRef {
    data: String,
    ptr: *const u8,
    _pin: PhantomPinned,
}

impl SelfRef {
    fn new(s: &str) -> Pin<Box<Self>> {
        let mut b = Box::pin(SelfRef { data: s.into(), ptr: std::ptr::null(), _pin: PhantomPinned });
        let p = b.data.as_ptr();
        unsafe { Pin::get_unchecked_mut(b.as_mut()).ptr = p; }
        b
    }
}
```

Это скорее иллюстрация механики. В реальном коде самоссылочные конструкции обычно прячут внутри библиотек, например в Future от async.

### 14. Что такое Pin и как его правильно понимать

Pin<P> это обертка над указателем, которая гарантирует, что значение, на которое он указывает, больше не будет перемещаться, если только тип не реализует Unpin. Большинство типов Unpin автоматически, и для них Pin ничем не отличается от обычного указателя. Pin нужен в первую очередь для async, потому что сгенерированные стейт машины могут быть самоссылочными.

Практически программисту приложений важно знать одно. Если функция принимает Pin<&mut Self>, значит за этим обычно стоит Future или другой стейтфул объект, который нельзя двигать.

```rust
use std::pin::Pin;
use std::future::Future;
use std::task::{Context, Poll};

struct Done;
impl Future for Done {
    type Output = ();
    fn poll(self: Pin<&mut Self>, _cx: &mut Context<'_>) -> Poll<()> {
        Poll::Ready(())
    }
}
```

Здесь Pin<&mut Self> не дает реализации полла случайно вынести self из своей памяти.

### 15. Что такое PhantomData и зачем он бывает нужен

PhantomData<T> это нулевой по размеру маркер, который говорит компилятору, что тип логически содержит или владеет T, хотя физически нет. Влияет на вариантность, на ограничения Drop и на трассировку лайфтаймов. Используется в обертках над сырыми указателями, в FFI, при реализации коллекций.

```rust
use std::marker::PhantomData;

struct Id<T> { value: u64, _t: PhantomData<T> }

struct User; struct Order;

fn main() {
    let u: Id<User> = Id { value: 1, _t: PhantomData };
    let o: Id<Order> = Id { value: 1, _t: PhantomData };
    let _ = (u.value, o.value); // u и o разные типы, перепутать нельзя
}
```

Это типобезопасные идентификаторы без рантайм оверхеда. Очень частый паттерн в крупных кодовых базах.

## Типы, трейты, обобщения

### 16. Чем структура отличается от enum

Структура это произведение типов. Все поля присутствуют одновременно. Enum это сумма типов. В любой момент активен ровно один вариант. Эту разницу важно понимать, потому что в Rust enum полноценный алгебраический тип, не как в C. Каждый вариант может нести произвольные данные. Память enum занимает по размеру самого большого варианта плюс дискриминант. Компилятор умеет ужимать представление, если есть niche, например None в Option<&T> кодируется нулевым указателем.

```rust
enum Shape {
    Circle(f64),
    Rect { w: f64, h: f64 },
}

fn area(s: &Shape) -> f64 {
    match s {
        Shape::Circle(r) => std::f64::consts::PI * r * r,
        Shape::Rect { w, h } => w * h,
    }
}

fn main() { println!("{}", area(&Shape::Rect { w: 2.0, h: 3.0 })); }
```

match заставляет покрыть все варианты, и забыть про новый случай при расширении enum компилятор не даст.

### 17. Что такое трейт и чем он отличается от интерфейса в Java

Трейт это набор методов и ассоциированных элементов, который тип может реализовать. От интерфейсов в Java отличается тем, что реализацию можно писать в другом модуле, чем сам тип, при условии соблюдения orphan rule. Трейты поддерживают дефолтные методы, ассоциированные типы и константы, могут быть обобщенными. Диспетчеризация по умолчанию статическая, через мономорфизацию, но можно сделать динамическую через dyn Trait.

```rust
trait Greet {
    fn name(&self) -> &str;
    fn hello(&self) { println!("hi {}", self.name()); }
}

struct Cat;
impl Greet for Cat { fn name(&self) -> &str { "cat" } }

fn main() { Cat.hello(); }
```

Дефолтный hello переиспользуется любым типом, который дал свою name.

### 18. Статическая и динамическая диспетчеризация, плюсы и минусы

Статическая диспетчеризация это generics с мономорфизацией. Компилятор генерирует свою копию функции под каждый конкретный тип. Быстрее в рантайме, заинлайнено, но раздувает бинарник и увеличивает время компиляции. Динамическая диспетчеризация это dyn Trait. Используется vtable, вызов через указатель. Бинарник меньше, типы можно смешивать в одном Vec<Box<dyn Trait>>, но есть стоимость косвенного вызова и невозможность инлайна.

```rust
trait Op { fn run(&self) -> i32; }
struct A; impl Op for A { fn run(&self) -> i32 { 1 } }
struct B; impl Op for B { fn run(&self) -> i32 { 2 } }

fn sum_static<T: Op>(x: &T, y: &T) -> i32 { x.run() + y.run() }
fn sum_dyn(ops: &[Box<dyn Op>]) -> i32 { ops.iter().map(|o| o.run()).sum() }
```

Выбор в проде такой. Если типы известны и набор маленький, generics. Если плагины, гетерогенные коллекции, конфигурация в рантайме, dyn.

### 19. Что такое object safety и почему не любой трейт может быть dyn

Чтобы трейт можно было использовать как dyn Trait, он должен быть object safe. Главные ограничения такие. Методы не принимают и не возвращают Self по значению, не используют дженерики, не имеют where Self: Sized без отдельного маркера. Self не появляется в ассоциированных константах. Причина в том, что для vtable нужен фиксированный набор слотов с известными сигнатурами. Если бы метод принимал Self, размер аргумента зависел бы от конкретного типа, и универсальный vtable стал бы невозможен.

```rust
trait Bad { fn make() -> Self; }            // не object safe
trait Good { fn name(&self) -> &str; }      // object safe

fn use_good(x: &dyn Good) { println!("{}", x.name()); }
```

Если очень хочется иметь и dyn, и generic метод, обычно разделяют трейт на два или используют where Self: Sized для отдельных методов.

### 20. Ассоциированные типы и дженерик параметры трейта, в чем разница

Генерик параметр трейта позволяет реализовать трейт несколько раз для одного типа с разными параметрами. Ассоциированный тип фиксируется в реализации, один тип это одна Item. Iterator имеет ассоциированный Item, потому что для одного типа естественно одно Item. From наоборот имеет generic параметр, потому что один тип может конвертироваться из многих других.

```rust
trait Counter { type Item; fn next(&mut self) -> Option<Self::Item>; }

struct UpTo { i: u32, end: u32 }
impl Counter for UpTo {
    type Item = u32;
    fn next(&mut self) -> Option<u32> {
        if self.i < self.end { self.i += 1; Some(self.i - 1) } else { None }
    }
}
```

Если бы Item был обычным параметром, в коде пришлось бы постоянно его уточнять, и эргономика провисла.

### 21. Что такое orphan rule и зачем он нужен

Правило сирот гласит, что реализовать трейт для типа можно только если либо трейт, либо тип определены в том же крейте. Это нужно, чтобы две сторонние библиотеки не сделали независимо несовместимые реализации одного и того же трейта для одного и того же типа. Когерентность системы трейтов держится именно на этом правиле. Обход обычно делают через newtype.

```rust
use std::fmt::Display;

struct Wrap(Vec<i32>);

impl Display for Wrap {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        write!(f, "{:?}", self.0)
    }
}
```

Wrap локальный, поэтому реализация Display для него разрешена.

### 22. Что такое newtype и зачем он применяется

Newtype это структура с одним полем, оборачивающая другой тип. Применений много. Соблюдение orphan rule, типобезопасность доменных значений, скрытие представления, разные реализации трейтов для одного базового типа. В рантайме newtype бесплатен, потому что layout совпадает с внутренним типом, и часто компилятор инлайнит обертку полностью.

```rust
struct Meters(f64);
struct Seconds(f64);

fn speed(d: Meters, t: Seconds) -> f64 { d.0 / t.0 }

fn main() { println!("{}", speed(Meters(100.0), Seconds(9.58))); }
```

Перепутать метры и секунды компилятор не даст. Это дешевая статическая защита от глупых багов.

### 23. Что такое derive и какие трейты обычно автоматически выводятся

#[derive(...)] это атрибут, который запускает соответствующий процедурный макрос и генерирует реализацию трейта. Стандартные derivable трейты это Debug, Clone, Copy, PartialEq, Eq, Hash, Default, PartialOrd, Ord. Они работают, если у всех полей структуры или вариантов enum уже есть нужная реализация. Помимо стандартных, derive часто используют для Serialize, Deserialize, thiserror::Error, strum.

```rust
#[derive(Debug, Clone, PartialEq, Eq, Hash, Default)]
struct Point { x: i32, y: i32 }

fn main() {
    let p = Point::default();
    println!("{:?}", p.clone());
}
```

Derive это про эргономику и про защиту от ошибок при рефакторинге. Добавили поле, и все реализации обновились автоматически.

### 24. Что такое impl Trait в позиции возврата и в позиции аргумента

В позиции возврата impl Trait означает один конкретный, но непоименованный тип, реализующий трейт. Используется чаще всего для возврата итераторов и замыканий, чтобы не писать длинные типы. Тип фиксируется внутри функции и одинаков для всех вызовов. В позиции аргумента impl Trait это просто короткая запись для дженерика, эквивалентно T: Trait.

```rust
fn iter_evens(v: &[i32]) -> impl Iterator<Item = &i32> {
    v.iter().filter(|x| *x % 2 == 0)
}

fn log(item: impl std::fmt::Display) { println!("{}", item); }
```

С возвращаемым impl Trait нужно помнить, что лайфтаймы захваченных аргументов попадают в скрытый тип. С 2024 edition правила захвата стали более явными.

### 25. dyn Trait в полях структуры, что нужно знать

dyn Trait это unsized тип. Положить его в поле структуры напрямую нельзя, нужен указатель. Чаще всего это Box<dyn Trait>, реже &dyn Trait, Rc или Arc. При выборе важно решить, кто владеет объектом. Если структура живет долго и должна владеть, обычно Box или Arc. Если структура только использует чужой объект, &dyn с лайфтаймом.

```rust
trait Logger { fn log(&self, msg: &str); }

struct App { logger: Box<dyn Logger + Send + Sync> }

struct Console;
impl Logger for Console { fn log(&self, m: &str) { println!("{}", m); } }

fn main() {
    let app = App { logger: Box::new(Console) };
    app.logger.log("ok");
}
```

Типичный паттерн внедрения зависимостей. Send и Sync добавлены, чтобы App можно было передавать между потоками.

### 26. Что такое Sized, ?Sized и зачем это

Sized это трейт, который реализуют все типы с известным на этапе компиляции размером. Это i32, String, &T, Box<T>. Не Sized это str, [T], dyn Trait. С такими типами нельзя работать по значению, только через указатель. По умолчанию у любого дженерика стоит неявное T: Sized. Если нужно принимать DST, явно пишут T: ?Sized.

```rust
fn print_ref<T: ?Sized + std::fmt::Debug>(x: &T) {
    println!("{:?}", x);
}

fn main() {
    print_ref::<str>("hello");
    print_ref::<[i32]>(&[1, 2, 3]);
}
```

Без ?Sized такой код не собрался бы для str и среза.

### 27. Что такое where clause и когда она нужнее, чем inline ограничения

Where позволяет описывать ограничения отдельно от списка параметров. Это удобно, когда ограничений много или они сложные. Например, ограничение на ассоциированный тип. T: Iterator, T::Item: Display. Записать это в угловых скобках громоздко. where в большом коде еще полезен тем, что выравнивает ограничения вертикально и упрощает диффы.

```rust
use std::fmt::Display;

fn print_all<I>(iter: I) where I: IntoIterator, I::Item: Display {
    for x in iter { println!("{}", x); }
}

fn main() { print_all(vec!["a", "b"]); }
```

При усложнении сигнатур where почти всегда читается лучше, чем длинная строка в угловых скобках.

### 28. Что такое coherence и блансировка реализаций

Когерентность это свойство системы трейтов, при котором для каждой пары тип трейт существует не более одной реализации, видимой во всей программе. Без когерентности один и тот же вызов в разных местах мог бы попадать в разные реализации, и поведение программы стало бы непредсказуемым. На уровне правил это поддерживается orphan rule и запретом перекрывающихся реализаций. Specialization, который частично позволяет иметь более специфичные реализации, до сих пор в стабильном виде не доехал именно по этой причине.

Компилятор отказывается принимать любую пару реализаций, которые потенциально могут пересекаться.

```rust
// Не соберется, если раскомментировать обе реализации.
// trait Foo {}
// impl<T> Foo for T {}
// impl Foo for i32 {}
```

Комментарий простой. Если хочется специализировать, сейчас приходится обходить это вручную через mini specialization паттерны.

### 29. Что такое supertrait и зачем он бывает нужен

Supertrait это требование, что любой тип, реализующий данный трейт, должен также реализовывать другой. Записывается как trait Child: Parent. Это позволяет вызывать методы родителя на &dyn Child и сужает множество реализаций. Полезно, когда родительский трейт дает базовые методы, а дочерний расширяет логику.

```rust
use std::fmt::Display;

trait Pretty: Display {
    fn pretty(&self) -> String { format!("=> {}", self) }
}

impl Pretty for i32 {}

fn main() { println!("{}", 7i32.pretty()); }
```

В методе pretty можно использовать любой метод Display прямо через self.

### 30. Что такое blanket implementation и где она применяется в стандартной библиотеке

Blanket impl это реализация трейта для всех типов, удовлетворяющих какому то ограничению. Самые известные примеры из стандартной библиотеки это impl<T: Display> ToString for T и impl<T, U> Into<U> for T where U: From<T>. Первый автоматически дает метод to_string для всего, что умеет печататься. Второй автоматически дает Into, как только написана From. Это очень мощный механизм, но он же конфликтует с orphan rule, потому что после blanket добавить ручную реализацию для пересекающегося типа уже нельзя.

```rust
struct Celsius(f64);
struct Fahrenheit(f64);

impl From<Celsius> for Fahrenheit {
    fn from(c: Celsius) -> Self { Fahrenheit(c.0 * 1.8 + 32.0) }
}

fn main() {
    let f: Fahrenheit = Celsius(100.0).into(); // into получено через blanket
    println!("{}", f.0);
}
```

Здесь руками написана только From, а Into подъехала бесплатно через стандартный blanket.

## Конкурентность и параллелизм

### 31. Send и Sync, в чем разница и как они выводятся

Send означает, что значение типа можно безопасно передать в другой поток. Sync означает, что &T можно безопасно делить между потоками, то есть T реализует Sync, если &T реализует Send. Оба трейта auto traits, компилятор сам выводит реализацию по полям. Не Send Rc, потому что счетчик не атомарный. Не Send и не Sync сырые указатели в обертках вроде Cell, потому что мутируют через shared ссылку без синхронизации.

```rust
use std::sync::Arc;
use std::thread;

fn main() {
    let v = Arc::new(vec![1, 2, 3]);
    let v2 = v.clone();
    thread::spawn(move || println!("{:?}", v2)).join().unwrap();
}
```

Если заменить Arc на Rc, компилятор откажется собирать, потому что Rc не Send.

### 32. Чем Mutex отличается от RwLock и когда какой выбирать

Mutex дает эксклюзивный доступ. В любой момент только один поток внутри секции. RwLock разрешает либо одного писателя, либо несколько читателей одновременно. RwLock дороже на вход и выход, и при коротких критических секциях обычно проигрывает Mutex даже на читающей нагрузке. Имеет смысл, когда читатели держат лок долго, а писатели редки.

```rust
use std::sync::RwLock;

fn main() {
    let lock = RwLock::new(0);
    {
        let r1 = lock.read().unwrap();
        let r2 = lock.read().unwrap();
        println!("{} {}", *r1, *r2);
    }
    *lock.write().unwrap() = 5;
}
```

Из практики. Если не уверены, начинать с Mutex. Менять на RwLock только после измерения, и не в любом стиле, а с учетом приоритета писателей, иначе можно получить starvation.

### 33. Что такое poisoning у Mutex и как с ним жить

Если поток упал с паникой, удерживая Mutex, лок становится отравленным. Все последующие попытки lock возвращают Err. Это сделано, чтобы случайно не работать с потенциально невалидным состоянием. Часто разумно прочитать данные через into_inner или PoisonError::into_inner и продолжить, если инвариант не нарушен. В новых проектах parking_lot::Mutex обычно предпочитают, у него нет poisoning и он быстрее.

```rust
use std::sync::Mutex;

fn main() {
    let m = Mutex::new(0);
    let _ = std::panic::catch_unwind(|| {
        let _g = m.lock().unwrap();
        panic!("boom");
    });
    match m.lock() {
        Ok(g) => println!("{}", *g),
        Err(p) => println!("poisoned, value = {}", *p.into_inner()),
    }
}
```

Ключ в том, что Rust не дает молча проигнорировать факт паники под локом.

### 34. Channel в std::sync::mpsc, его особенности

Канал mpsc это многопроизводитель один потребитель. Передача по значению, отправитель Send, приемник Send но не Sync. Каналы строятся вокруг неограниченной очереди. Это удобно, но опасно. Если получатель медленнее отправителей, память растет. На практике часто используют crossbeam-channel и tokio mpsc, у них есть bounded варианты, select, поддержка отмены.

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();
    for i in 0..3 {
        let tx = tx.clone();
        thread::spawn(move || tx.send(i).unwrap());
    }
    drop(tx);
    for v in rx { println!("{}", v); }
}
```

Цикл for v in rx завершается, когда все клоны tx уничтожены. Поэтому важно сбросить исходный tx, иначе будет дедлок.

### 35. Что такое scoped threads и зачем они появились в стандартной библиотеке

До стабилизации std::thread::scope для передачи ссылок в поток приходилось либо использовать Arc, либо crate crossbeam. Scoped threads гарантируют, что все потоки внутри scope завершатся до выхода из него, поэтому компилятор разрешает заимствовать стек вызывающего без 'static. Это убрало целый класс лишних аллокаций и упростил код.

```rust
use std::thread;

fn main() {
    let data = vec![1, 2, 3, 4];
    thread::scope(|s| {
        s.spawn(|| println!("{:?}", &data[..2]));
        s.spawn(|| println!("{:?}", &data[2..]));
    });
}
```

После scope data все еще доступна. Никаких клонов и Arc.

### 36. Atomic типы, что такое memory ordering и какие порядки бывают

Atomic типы дают неблокирующие операции с явным memory ordering. Доступные порядки это Relaxed, Acquire, Release, AcqRel, SeqCst. Relaxed гарантирует только атомарность самой операции. Acquire запрещает реордеринг последующих чтений выше себя. Release запрещает реордеринг предыдущих записей ниже себя. SeqCst дает глобальный порядок. На практике большинство кода обходится парой Acquire и Release для flag паттернов, а SeqCst используется, когда лень думать, либо когда действительно нужен тотальный порядок.

```rust
use std::sync::atomic::{AtomicUsize, Ordering};
use std::thread;

static CNT: AtomicUsize = AtomicUsize::new(0);

fn main() {
    let h: Vec<_> = (0..4).map(|_| thread::spawn(|| {
        for _ in 0..1000 { CNT.fetch_add(1, Ordering::Relaxed); }
    })).collect();
    for t in h { t.join().unwrap(); }
    println!("{}", CNT.load(Ordering::Relaxed));
}
```

Для простого счетчика Relaxed достаточно, потому что важна только финальная сумма, а не порядок инкрементов.

### 37. Что такое гонка данных и чем она отличается от race condition

Гонка данных это конкретная ситуация, когда два потока обращаются к одной памяти без синхронизации, и хотя бы один пишет. В безопасном Rust таких гонок нет благодаря системе типов и трейтам Send Sync. Race condition это более широкое понятие, логическая гонка по времени. Например, проверили условие, потом что то сделали, а между этими шагами другой поток уже изменил состояние. Гонок данных Rust не допустит, race condition в логике вполне может быть.

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let m = Arc::new(Mutex::new(false));
    let m2 = m.clone();
    let h = thread::spawn(move || {
        let mut g = m2.lock().unwrap();
        if !*g { *g = true; }
    });
    h.join().unwrap();
    println!("{}", *m.lock().unwrap());
}
```

Лок здесь решает не гонку данных, а именно атомарность пары чтение запись.

### 38. Что такое deadlock и как его избегать в Rust

Дедлок это ситуация, когда несколько потоков ждут друг друга по кругу и ни один не может продвинуться. Классически возникает при захвате нескольких локов в разном порядке. Базовый рецепт. Всегда брать локи в одном фиксированном порядке. Минимизировать критические секции. По возможности использовать try_lock и таймауты. В асинхронном коде дедлок легко получить, удерживая лок через await. Лучше явно отпустить лок перед await.

```rust
use std::sync::Mutex;

fn safe(m: &Mutex<i32>) -> i32 {
    let v = { let g = m.lock().unwrap(); *g };
    v + 1
}

fn main() {
    let m = Mutex::new(10);
    println!("{}", safe(&m));
}
```

Лок берется в блоке и сразу отпускается. Дальнейшая логика выполняется без удерживания.

### 39. Rayon, как он работает и где его уместно применять

Rayon это библиотека параллельной обработки данных с work stealing. Главная сильная сторона это адаптер par_iter, который превращает обычный итератор в параллельный. Под капотом он рекурсивно делит работу на пары и распределяет задачи между потоками пула. Хорошо подходит для CPU bound задач над коллекциями. Плохо подходит для IO, для смешанных рабочих нагрузок с блокировками и для задач с сильной зависимостью между шагами.

```rust
use rayon::prelude::*;

fn main() {
    let sum: u64 = (1u64..=1_000_000).into_par_iter().map(|x| x * x).sum();
    println!("{}", sum);
}
```

Если в map встретится блокирующий вызов, поток пула будет занят, и parallelism деградирует. Это типичная ловушка при смешении rayon с синхронным IO.

### 40. Что такое work stealing и почему он эффективен

Work stealing это стратегия планирования, при которой каждый поток имеет собственную очередь задач и берет работу с ее головы. Когда у потока закончились свои задачи, он крадет задачу с хвоста очереди другого потока. Это снижает конкуренцию за общую очередь, дает хорошую локальность, потому что свежие задачи берутся свои, и при этом распределяет нагрузку. На этом принципе работают rayon, tokio multi thread, async-std.

Практический вывод. Если задачи короткие и однородные, work stealing справляется почти идеально. Если задачи разной длины, важно избегать слишком длинных, иначе они тормозят балансировку. В tokio то же самое означает не блокировать поток.

### 41. Что такое thread pool и почему ручное spawn не всегда хорошая идея

Создание потока операции не бесплатно. Это сискол, стек, регистрация в ядре. Если задачи короткие, тратить отдельный поток на каждую расточительно. Thread pool создает потоки заранее и переиспользует их. В Rust типовые решения это rayon::ThreadPool, tokio::runtime, threadpool. Спавн потока руками оправдан для долгоживущих сущностей, например для фонового логгера или для отдельного цикла обработки IO.

```rust
use rayon::ThreadPoolBuilder;

fn main() {
    let pool = ThreadPoolBuilder::new().num_threads(4).build().unwrap();
    let r = pool.install(|| (0..100).into_iter().sum::<i32>());
    println!("{}", r);
}
```

Явный пул удобен, когда нужно отделить горячие задачи от фоновых.

### 42. Что такое barrier и когда он нужен

Барьер синхронизирует группу потоков. Все потоки доходят до барьера и ждут, пока не подойдут все остальные, после чего проходят дальше одновременно. Используется в симуляциях по шагам, в параллельных алгоритмах, где фаза вычисления должна полностью закончиться до начала следующей. В Rust есть std::sync::Barrier.

```rust
use std::sync::{Arc, Barrier};
use std::thread;

fn main() {
    let b = Arc::new(Barrier::new(3));
    let mut h = vec![];
    for i in 0..3 {
        let b = b.clone();
        h.push(thread::spawn(move || {
            println!("{} before", i);
            b.wait();
            println!("{} after", i);
        }));
    }
    for t in h { t.join().unwrap(); }
}
```

Вывод гарантирует, что все before напечатаются до любого after.

### 43. Что такое condvar и когда он лучше, чем busy wait

Condvar это условная переменная. Поток, удерживая лок, ждет условие через wait. На время wait лок отпускается. Другой поток меняет состояние и вызывает notify_one или notify_all. После пробуждения wait автоматически снова берет лок. Это правильный способ ждать события, без сжигания процессора в цикле проверки.

```rust
use std::sync::{Arc, Condvar, Mutex};
use std::thread;

fn main() {
    let pair = Arc::new((Mutex::new(false), Condvar::new()));
    let pair2 = pair.clone();
    thread::spawn(move || {
        let (m, cv) = &*pair2;
        let mut g = m.lock().unwrap();
        *g = true;
        cv.notify_one();
    });
    let (m, cv) = &*pair;
    let mut g = m.lock().unwrap();
    while !*g { g = cv.wait(g).unwrap(); }
    println!("started");
}
```

Проверка в while нужна потому, что бывают spurious wakeups, и одного wait недостаточно.

### 44. Что такое spinlock и когда он оправдан

Spinlock это лок, который вместо блокировки потока крутится в цикле проверки. Имеет смысл только тогда, когда критическая секция очень короткая и переключение контекста было бы дороже самого ожидания. В прикладном коде это редкость. В драйверах и низкоуровневых либах встречается. В Rust стандартного spinlock нет, есть параметризованные реализации в crate spin. Но в большинстве случаев правильный ответ это parking_lot::Mutex, который сам решает, спинить или парковать.

### 45. Что такое thread local и где он реально нужен

Thread local это значение, у которого свой экземпляр в каждом потоке. В Rust это макрос thread_local! и тип LocalKey. Полезен для аллокаторов, для пер потокового кэша, для трассировки, для случайных генераторов. Важно понимать, что данные thread local не Send. Если попытаться унести из них что то в другой поток, надо клонировать.

```rust
use std::cell::RefCell;

thread_local! {
    static COUNTER: RefCell<u64> = RefCell::new(0);
}

fn bump() { COUNTER.with(|c| *c.borrow_mut() += 1); }

fn main() {
    bump(); bump();
    COUNTER.with(|c| println!("{}", c.borrow()));
}
```

Это частый паттерн для статистики и для тестового хука вместо глобального состояния.

## Async и runtime

### 46. Что такое async fn и во что он превращается компилятором

async fn это синтаксический сахар над функцией, возвращающей impl Future. Тело функции трансформируется в стейт машину. Каждое .await это точка приостановки. Локальные переменные, живущие через .await, превращаются в поля стейт машины. Сама функция при вызове не делает работу, а возвращает фьючу. Работа начинается только когда фьючу опрашивает рантайм.

```rust
async fn add(a: u32, b: u32) -> u32 { a + b }

#[tokio::main]
async fn main() {
    let f = add(1, 2);          // ничего еще не вычислено
    let r = f.await;             // только сейчас полл и результат
    println!("{}", r);
}
```

Эта ленивость отличает Rust от языков, где async eager.

### 47. Что такое Future и как работает poll

Future это трейт с одним методом poll. Поллер передает Context с Waker. Реализация делает шаг вперед и возвращает Poll::Ready, если работа закончена, или Poll::Pending, если нужно подождать. Если вернули Pending, реализация обязана где то сохранить waker и вызвать его, когда сможет продвинуться. Иначе фьюча зависнет. Рантайм не опрашивает фьючи в цикле, он реагирует на пробуждения.

```rust
use std::future::Future;
use std::pin::Pin;
use std::task::{Context, Poll};

struct Yield(bool);
impl Future for Yield {
    type Output = ();
    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<()> {
        if self.0 { Poll::Ready(()) } else {
            self.0 = true;
            cx.waker().wake_by_ref();
            Poll::Pending
        }
    }
}
```

Yield один раз отдает управление и сразу будит сам себя. Простой способ дать рантайму прокрутить очередь.

### 48. Tokio и async-std, в чем разница и что выбирать

Tokio это де факто стандарт. Большой набор примитивов, мощный планировщик, экосистема. async-std ставил целью повторить API стандартной библиотеки, но в практике почти весь крупный код в индустрии написан под tokio. Сейчас async-std в значительной мере legacy. Выбор простой. Если проект не имеет жестких требований, берется tokio. Если хочется минимального рантайма для embedded, есть smol, embassy.

### 49. Что такое executor и reactor в async

Executor отвечает за то, чтобы поллить фьючи, когда их нужно поллить. Reactor отвечает за регистрацию событий ввода вывода в ядре и за пробуждение wakers, когда событие пришло. В tokio это реализовано через mio. Когда сокет становится готов, mio будит соответствующий waker, executor добавляет таску в очередь, и фьюча получает следующий polл.

Понимать эту пару важно, потому что многие странности async объясняются разделением ответственности. Если фьюча не двигается, либо ее не разбудили, либо executor не дошел до очереди.

### 50. Кооперативная многозадачность и почему нельзя блокировать поток в async

В async коде один поток выполняет много задач. Пока задача не отдала управление через await, никакая другая не выполняется на этом потоке. Если внутри async fn вызвать std::thread::sleep или сделать тяжелый sync IO, остальные задачи на этом же рабочем потоке встанут. В tokio есть spawn_blocking, который отправляет работу на отдельный пул блокирующих потоков. Это правильный путь для CPU bound или для синхронных API.

```rust
#[tokio::main]
async fn main() {
    let r = tokio::task::spawn_blocking(|| heavy()).await.unwrap();
    println!("{}", r);
}

fn heavy() -> u64 { (0..1_000_000u64).sum() }
```

Логика простая. Все, что может занять больше микросекунды без await, отправляется в spawn_blocking.

### 51. Что такое tokio::select и какие у него подводные камни

select позволяет ждать одновременно несколько фьюч и продолжить, как только одна из них готова. Остальные фьючи дропаются. Это и есть основная ловушка. Если внутри ветки уже была выполнена часть работы с побочным эффектом, дропнутая фьюча не доведет работу до конца. Поэтому при использовании select важно либо использовать cancel safe примитивы, либо явно сохранять состояние через future::pin и biased.

```rust
use tokio::time::{sleep, Duration};

#[tokio::main]
async fn main() {
    tokio::select! {
        _ = sleep(Duration::from_millis(50)) => println!("timeout"),
        _ = async { sleep(Duration::from_millis(100)).await; } => println!("inner"),
    }
}
```

Здесь сработает таймаут, а вторая ветка будет отменена.

### 52. Cancel safety, что это и почему важно

Cancel safety означает, что фьюча может быть дропнута на любом await без нарушения инвариантов. Многие операции tokio cancel safe, например чтение из канала. Многие не cancel safe, например AsyncReadExt::read_exact, который при отмене может оставить буфер частично прочитанным. В коде, который использует select, надо знать про cancel safety используемых API. В документации tokio это явно отмечено.

### 53. Что такое spawn и join в tokio

tokio::spawn отправляет фьючу на исполнение в рантайм и возвращает JoinHandle. Сама задача начинает работать немедленно. JoinHandle это фьюча с результатом. Через await на хендле можно дождаться завершения и забрать значение. Если хендл уронить, задача продолжит работать в фоне. Чтобы прервать, можно вызвать abort.

```rust
#[tokio::main]
async fn main() {
    let h = tokio::spawn(async { 42 });
    println!("{}", h.await.unwrap());
}
```

Задача в spawn должна быть 'static и Send для multi thread рантайма. Для single thread достаточно 'static.

### 54. Что такое JoinSet и зачем он нужен

JoinSet это структура для управления группой задач. Позволяет ждать завершения любого из них через join_next, отменять все через shutdown, ограничивать число параллельно работающих. По сравнению с FuturesUnordered удобнее именно для tokio задач, потому что хранит JoinHandle и корректно обрабатывает abort.

```rust
use tokio::task::JoinSet;

#[tokio::main]
async fn main() {
    let mut set = JoinSet::new();
    for i in 0..5 { set.spawn(async move { i * i }); }
    while let Some(r) = set.join_next().await {
        println!("{}", r.unwrap());
    }
}
```

Это типовой паттерн fan out fan in.

### 55. Что такое async trait и почему он нетривиален

async fn в трейтах долгое время не было, потому что Future это разный тип у каждой реализации. Сейчас в стабильном Rust async fn в трейтах работает напрямую, но с ограничениями для dyn. Для dyn trait сейчас используют либо макрос async_trait, либо вручную возвращают Box<dyn Future>. async_trait делает примерно это под капотом, добавляя аллокацию на каждый вызов. Для горячих путей это критично.

```rust
use async_trait::async_trait;

#[async_trait]
trait Store {
    async fn get(&self, key: &str) -> Option<String>;
}

struct Mem;
#[async_trait]
impl Store for Mem {
    async fn get(&self, _k: &str) -> Option<String> { Some("v".into()) }
}
```

Если динамическая диспетчеризация не нужна, лучше использовать обычный async fn в трейте и не платить за box.

### 56. Backpressure и как его делать в async

Backpressure это давление потребителя на производителя. Без него быстрый продюсер забивает память. В асинхронных конвейерах backpressure реализуется через bounded каналы и через ограничение параллелизма. В tokio есть mpsc::channel с capacity, у него send становится фьючей, которая ждет, пока в очереди освободится место. Это автоматически тормозит продюсера.

```rust
use tokio::sync::mpsc;

#[tokio::main]
async fn main() {
    let (tx, mut rx) = mpsc::channel::<i32>(8);
    tokio::spawn(async move {
        for i in 0..100 { tx.send(i).await.unwrap(); }
    });
    while let Some(v) = rx.recv().await { println!("{}", v); }
}
```

Если получатель медленный, send в задаче будет ждать. Память не растет бесконтрольно.

### 57. Streams в async, что это и где применяются

Stream это асинхронный аналог Iterator. Метод poll_next возвращает Poll<Option<Item>>. Стримы используются для обработки потоков сообщений, событий, чанков из сети, строк из файла. В крейтах futures и tokio_stream есть набор адаптеров map filter try_next chunks throttle.

```rust
use tokio_stream::{self as stream, StreamExt};

#[tokio::main]
async fn main() {
    let mut s = stream::iter(vec![1, 2, 3, 4, 5]).filter(|x| x % 2 == 0);
    while let Some(v) = s.next().await { println!("{}", v); }
}
```

Стримы хорошо ложатся на любую event driven архитектуру. Каждый шаг ленивый, кроме того, что нужно для прокачки следующего элемента.

### 58. Что такое pin_project и зачем он нужен

Когда пишешь свою фьючу или стрим со сложной структурой, поля надо проектировать с учетом Pin. Какие то поля должны оставаться запиненными, какие то нет. pin_project это макрос, который генерирует безопасный API доступа к полям без unsafe. Без него пришлось бы писать вручную через Pin::map_unchecked_mut, а это легко превращается в UB.

```rust
use pin_project::pin_project;
use std::pin::Pin;
use std::future::Future;
use std::task::{Context, Poll};

#[pin_project]
struct Then<F> { #[pin] fut: F, n: u32 }

impl<F: Future<Output = u32>> Future for Then<F> {
    type Output = u32;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<u32> {
        let this = self.project();
        match this.fut.poll(cx) {
            Poll::Ready(v) => Poll::Ready(v + *this.n),
            Poll::Pending => Poll::Pending,
        }
    }
}
```

project дает Pin<&mut F> для запиненного поля и &mut u32 для обычного. Никакого unsafe в пользовательском коде.

### 59. Что такое executor budget в tokio и как его исчерпание влияет на код

Tokio начисляет каждой задаче бюджет в poll операциях. Когда задача исчерпала бюджет, кооперативный yield заставляет ее отдать управление, даже если она готова продолжить. Это защищает от ситуации, когда одна тяжелая задача занимает рабочий поток. Если задача делает много синхронной работы между awaits, бюджет тратится медленно, и можно случайно стать тем самым горячим воркером. Решение либо явные tokio::task::yield_now, либо вынесение в spawn_blocking.

### 60. Что такое LocalSet и когда он нужен

LocalSet позволяет запускать !Send фьючи на одном потоке. Используется для задач, чьи внутренности нельзя двигать между потоками, типичный пример это интеграция с библиотеками, которые держат не Send состояние. В multi thread рантайме обычные spawn требуют Send, а LocalSet снимает это требование, привязывая задачи к текущему потоку.

```rust
use std::rc::Rc;
use tokio::task;

#[tokio::main(flavor = "current_thread")]
async fn main() {
    let local = task::LocalSet::new();
    local.run_until(async {
        let r = Rc::new(1);
        task::spawn_local(async move { println!("{}", r); }).await.unwrap();
    }).await;
}
```

Здесь Rc, который не Send, спокойно живет в spawn_local.

### 61. Что такое timeout и как его делать в tokio

Для ограничения времени операции используется tokio::time::timeout. Он оборачивает фьючу и возвращает Result, где Err это Elapsed. Если внутри был критичный ресурс, важно, что фьюча будет дропнута. См. cancel safety. Иначе можно оставить полузаписанный буфер или незакрытое соединение.

```rust
use tokio::time::{timeout, sleep, Duration};

#[tokio::main]
async fn main() {
    let r = timeout(Duration::from_millis(50), sleep(Duration::from_millis(100))).await;
    println!("{:?}", r);
}
```

Вывод Err(Elapsed). Удобно для защиты от подвисших внешних вызовов.

### 62. Структурированная конкурентность, как ее делать в Rust

Идея структурированной конкурентности в том, что все дочерние задачи завершаются до того, как функция, которая их породила, вернет управление. Это упрощает рассуждение об ошибках и о времени жизни данных. В Rust на стандартной библиотеке такой паттерн строится через std::thread::scope. В async аналогов в std пока нет, но JoinSet, tokio_scoped, async-scoped или ручной select с graceful shutdown играют ту же роль.

```rust
use tokio::task::JoinSet;

async fn run() {
    let mut set = JoinSet::new();
    for i in 0..4 { set.spawn(async move { println!("{}", i); }); }
    while set.join_next().await.is_some() {}
}

#[tokio::main]
async fn main() { run().await; }
```

Когда run завершается, все задачи гарантированно отработали. Это и есть структурированный подход.

## Unsafe, FFI, низкий уровень

### 63. Что разрешает unsafe и что он не отключает

Unsafe разрешает пять вещей. Разыменование сырого указателя, вызов unsafe функции или метода, доступ или изменение mutable static, реализацию unsafe трейта, обращение к union. Все остальные проверки компилятора остаются. Заимствование, типобезопасность, синтаксис, всё это работает как обычно. Unsafe не делает код быстрее само по себе и не отключает borrow checker.

```rust
fn main() {
    let mut x = 10;
    let p = &mut x as *mut i32;
    unsafe { *p += 1; }
    println!("{}", x);
}
```

Ключ в том, что ответственность за инварианты в этом блоке программист берет на себя.

### 64. Что такое undefined behavior в Rust и какие самые частые причины UB

UB это поведение, для которого язык не дает никаких гарантий. Компилятор имеет право предполагать, что UB не возникает, и оптимизировать с учетом этого. В Rust типичные источники UB. Гонка данных через unsafe. Висячий указатель. Алиасинг ссылок несовместимым образом, например &mut и & одновременно через сырой указатель. Чтение неинициализированной памяти. Нарушение invariant Strict Aliasing для типизированных указателей. Передача невалидных значений примитивов, например bool со значением 2.

Правильная модель здесь такая. Любой unsafe должен иметь рядом комментарий с обоснованием, почему инварианты соблюдены.

### 65. raw pointers vs references, что и когда использовать

Ссылки это безопасный примитив с гарантиями валидности и алиасинга. Сырые указатели *const T и *mut T этих гарантий не дают, не имеют лайфтайма и могут быть null. В прикладном коде сырые указатели почти не нужны. Появляются в FFI, в реализациях коллекций, в работе с памятью на низком уровне.

```rust
fn main() {
    let mut v = vec![1, 2, 3];
    let p: *mut i32 = v.as_mut_ptr();
    unsafe { *p.add(1) = 20; }
    println!("{:?}", v);
}
```

Индекс через сырой указатель не проверяется на выход за границы. Программист отвечает за это сам.

### 66. MaybeUninit, зачем он нужен

MaybeUninit<T> это обертка, которая позволяет легально работать с неинициализированной памятью. Раньше для тех же целей использовали mem::uninitialized, но это давало UB для типов с непустыми инвариантами, например для bool или NonNull. MaybeUninit обходит это, потому что компилятор знает, что внутри может быть мусор, и не делает предположений.

```rust
use std::mem::MaybeUninit;

fn make_array() -> [u32; 4] {
    let mut arr: [MaybeUninit<u32>; 4] = unsafe { MaybeUninit::uninit().assume_init() };
    for (i, slot) in arr.iter_mut().enumerate() {
        slot.write(i as u32);
    }
    unsafe { std::mem::transmute(arr) }
}

fn main() { println!("{:?}", make_array()); }
```

Классический паттерн для построения массивов без лишних инициализаций.

### 67. Что такое UnsafeCell и почему без него не сделать interior mutability

UnsafeCell это единственный легальный способ получить &mut T через &T. Все типы интерьорной мутабельности построены на нем. Сам по себе UnsafeCell не делает синхронизацию и не проверяет правила. Он только разрешает то, что иначе компилятор счел бы UB. Сверху уже строятся Cell, RefCell, Mutex, atomics. Поэтому если человек делает свой контейнер с интерьорной мутабельностью, начинать он будет с UnsafeCell.

### 68. FFI с C, что нужно знать про репрезентацию типов

По умолчанию layout структуры в Rust не определен. Для совместимости с C ставят #[repr(C)]. Тогда поля идут в порядке объявления с padding по правилам C ABI. Аналогично, для enum, экспортируемых в C, используют #[repr(C)] или явный примитив #[repr(u32)]. Все типы, передаваемые через FFI, должны быть FFI safe. Например, String и Vec нельзя передавать напрямую, надо использовать сырой указатель и длину.

```rust
#[repr(C)]
struct Point { x: f64, y: f64 }

extern "C" {
    fn distance(a: Point, b: Point) -> f64;
}
```

#[repr(C)] обязательна, иначе layout может не совпасть.

### 69. extern fn, calling conventions, panic через границу FFI

fn extern "C" задает соглашение вызова C. Без него используется внутренний Rust ABI, и интероп невозможен. Паника, вылетающая через границу FFI, это UB. Поэтому код, который вызывают из C, оборачивают в std::panic::catch_unwind. В Rust 2021 и новее unwinding через границу extern "C" по умолчанию приводит к abort, что само по себе уже спасает от UB, но обычно все равно явно ловят панику и возвращают код ошибки.

```rust
#[no_mangle]
pub extern "C" fn add(a: i32, b: i32) -> i32 {
    std::panic::catch_unwind(|| a + b).unwrap_or(-1)
}
```

Это базовый паттерн для библиотек, которые линкуются из C или Python.

### 70. bindgen, cbindgen, cxx, чем они отличаются

Bindgen генерирует Rust обвязки из C заголовков. Cbindgen наоборот, по Rust коду делает C заголовки. Cxx это безопасный интероп с C++, с проверкой совместимости типов на этапе сборки. Если задача переписать часть C либы на Rust, обычно используют bindgen и cbindgen. Если интегрироваться с C++, cxx, потому что unsafe extern "C++" с виртуальными методами руками поддерживать невозможно.

### 71. Что такое repr(transparent) и где он применяется

#[repr(transparent)] говорит, что структура с одним непрозрачным полем имеет такое же ABI и layout, как это поле. Используется в newtype паттернах, когда нужно передавать обертку через FFI или применять методы низкого уровня. Также обычно ставится на типы, реализующие интерьорную мутабельность.

```rust
#[repr(transparent)]
struct Wrapped(u32);

extern "C" { fn takes_u32(x: u32); }

fn main() {
    let w = Wrapped(7);
    unsafe { takes_u32(w.0); }
}
```

Wrapped по ABI неотличим от u32 и может безопасно использоваться в сигнатурах FFI.

### 72. Что такое no_std и где он применяется

no_std это режим без стандартной библиотеки. Доступны только core и при желании alloc. Используется в эмбеддед, в ядрах ОС, в WASM рантаймах, в bootloaders. Особенности. Нет std::io, std::thread, std::fs. Нет println. Нет паники по умолчанию, нужен panic handler. Часто нет аллокатора, используют статические буферы и crate heapless.

```rust
#![no_std]
#![no_main]

use core::panic::PanicInfo;

#[panic_handler]
fn panic(_info: &PanicInfo) -> ! { loop {} }

#[no_mangle]
pub extern "C" fn _start() -> ! { loop {} }
```

Это минимальный скелет no_std программы.

### 73. inline assembly в Rust, когда и как применяется

Макрос asm! позволяет писать ассемблер прямо внутри Rust. Полезен для интринзиков, которых нет в crate core_intrinsics, для управления регистрами в low level, для оптимизаций под конкретную архитектуру. Это очень узкая тема, в прикладе встречается редко. Использовать имеет смысл, когда измерения показывают, что компилятор не генерирует ожидаемые инструкции, и нет другого пути.

```rust
#[cfg(target_arch = "x86_64")]
fn rdtsc() -> u64 {
    let lo: u32; let hi: u32;
    unsafe { core::arch::asm!("rdtsc", out("eax") lo, out("edx") hi); }
    ((hi as u64) << 32) | lo as u64
}
```

Здесь читается счетчик циклов процессора.

### 74. SIMD в Rust, основные подходы

Есть два уровня. Платформенно специфичные интринзики в core::arch и портабельный std::simd, который пока в nightly как experimental. Прикладно проще использовать crate wide или packed_simd, либо положиться на автовекторизацию LLVM. Чтобы автовекторизация сработала, цикл должен иметь регулярную форму, без зависимостей по данным между итерациями, и работать со срезом известного типа.

```rust
fn sum(a: &[f32]) -> f32 {
    let mut s = 0.0;
    for &x in a { s += x; }
    s
}
```

LLVM на release с -C target-cpu=native такой код почти всегда векторизует. Сначала имеет смысл проверить это, а уже потом писать руками.

### 75. allocator API, что это и зачем оно

allocator API позволяет задать собственный аллокатор глобально через #[global_allocator] или локально для коллекций через Allocator. Глобальная замена часто используется для подключения jemalloc, mimalloc, snmalloc. Локальные аллокаторы полезны для арен, бамп аллокаторов и для эмбеддед, где память надо считать на байты.

```rust
use mimalloc::MiMalloc;

#[global_allocator]
static GLOBAL: MiMalloc = MiMalloc;

fn main() { let _ = vec![0u8; 1024]; }
```

Замена аллокатора нередко дает 5 15 процентов общего ускорения на нагруженных сервисах без правки бизнес кода.

### 76. mem::transmute, его опасности и альтернативы

transmute побитово реинтерпретирует значение одного типа как другой. Это одна из самых опасных функций в языке. Она безопасна, только если оба типа имеют одинаковый layout и значение остается валидным в новом типе. Например, перетранслировать u32 в f32 можно, потому что у обоих 4 байта. Перетранслировать u8 в bool нельзя, потому что bool не любое значение валидно. Безопасные альтернативы. from_bits для floats, методы to_ne_bytes from_ne_bytes для разбора, bytemuck и zerocopy для proven safe конверсий.

### 77. Что такое volatile операции и где они нужны

volatile это операции чтения и записи, которые компилятор не имеет права оптимизировать или переупорядочивать. В Rust это std::ptr::read_volatile и write_volatile. Нужны для работы с memory mapped регистрами устройств, где каждое чтение и каждая запись имеет побочный эффект на железо. В обычном многопоточном коде volatile не заменяет atomics. У них разные гарантии. Для синхронизации между потоками используется atomic, для общения с железом volatile.

### 78. Особенности написания собственного unsafe API

Главный принцип. Если функция unsafe, она должна явно документировать свои инварианты, что обязан гарантировать вызывающий. Если функция safe, она внутри может содержать unsafe, но снаружи должна быть невозможна никакая комбинация валидных аргументов и состояний, которая приводит к UB. Это называется sound API. Любое отступление это потенциальный security баг. Поэтому в библиотеках с большим unsafe принято писать раздел Safety в doc комментарии и покрывать код Miri.

```rust
/// # Safety
/// ptr должен указывать на валидный u8 буфер длиной не меньше len.
pub unsafe fn read_buf(ptr: *const u8, len: usize) -> Vec<u8> {
    std::slice::from_raw_parts(ptr, len).to_vec()
}
```

Документация это не косметика. Это контракт, без которого использовать unsafe правильно нельзя.

## Производительность

### 79. Как профилировать Rust код

Для CPU профайла стандартный инструмент это perf на Linux плюс flamegraph. Под капотом это сэмплирующий профайлер, который собирает стеки и строит дерево. Дополнительно используют cargo-flamegraph, который оборачивает запуск и сразу генерит svg. Для аллокаций есть heaptrack, dhat и crate dhat. Для async кода у tokio есть console подсистема через tokio-console, она показывает зависшие таски и долгоудерживаемые локи. Замеры микробенчмарков делают через criterion.

Практический подход. Сначала измерить, найти горячее место, потом править. Не наоборот. Угадывание узких мест в Rust почти всегда уходит мимо, потому что компилятор очень многое инлайнит.

### 80. Inlining, как им управлять и когда это полезно

Компилятор сам решает, что инлайнить, опираясь на размер функции, число вызовов, profile guided оптимизации. Атрибуты #[inline], #[inline(always)], #[inline(never)] дают подсказки. #[inline] нужен в первую очередь для функций в библиотеках, потому что без него вызов из другого crate не сможет быть заинлайнен. always стоит ставить редко, обычно для тонких оберток над интринзиками. Никогда полезен для холодного кода типа error reporting, чтобы он не раздувал горячий путь.

```rust
#[inline]
pub fn fast_add(a: u32, b: u32) -> u32 { a.wrapping_add(b) }
```

Для библиотечного crate такой атрибут практически обязателен на простых функциях.

### 81. Allocations, как их избегать в горячем коде

Каждая аллокация это поход в аллокатор, потенциально с локом. На горячем пути аллокации обычно главная стоимость. Способы их избегать. Использовать буферы, выделенные один раз и переиспользуемые. clear vs new. Применять методы collect_into и extend_from_slice вместо collect нового Vec. Использовать smallvec для коллекций, где обычно мало элементов. Использовать String::with_capacity и Vec::with_capacity, чтобы избежать ресайзов. По возможности возвращать &str или Cow вместо String.

```rust
fn build_lines(out: &mut String, n: u32) {
    out.clear();
    out.reserve(n as usize * 4);
    for i in 0..n {
        use std::fmt::Write;
        let _ = write!(out, "{}\n", i);
    }
}
```

out приходит снаружи и переиспользуется. Никакой новой String на каждом вызове.

### 82. Vec и его модель роста, capacity

Vec хранит указатель, длину и емкость. При переполнении вызывается реаллокация, которая копирует данные на новое место. Стратегия роста обычно удвоение, но конкретная реализация может отличаться. Если число элементов известно заранее, with_capacity дает только одну аллокацию. shrink_to_fit имеет смысл, если вектор больше не будет расти. Для часто переиспользуемых буферов лучше держать емкость и периодически делать clear.

```rust
fn main() {
    let mut v = Vec::with_capacity(1000);
    for i in 0..1000 { v.push(i); }
    println!("{} {}", v.len(), v.capacity());
}
```

Должен быть один промах в аллокаторе на тысячу push, а не десять.

### 83. String, str и работа с UTF-8

String это владеющий буфер UTF-8. &str это срез валидного UTF-8. Индексация по байтам разрешена через [..], но только по границам символов. По произвольному индексу будет паника. Для обработки символов используют методы chars, char_indices. Не любая операция в char это операция в UTF-8 байтах. Длина строки в символах считается через s.chars().count, а не через len. Это дорого, потому что O от количества байт.

```rust
fn main() {
    let s = "привет";
    println!("{} {}", s.len(), s.chars().count()); // 12 6
}
```

Если надо много раз спрашивать длину в символах, лучше один раз посчитать и кэшировать.

### 84. HashMap и hash DOS, что такое SipHash и зачем нужны другие хешеры

Стандартный HashMap использует SipHash 1 3 с рандомизированным ключом. Это защищает от hash flooding атак, но медленнее на коротких ключах, чем нелинейные альтернативы. Для внутренних, не атакоопасных карт часто берут ahash или fxhash. Они в 2 3 раза быстрее, но не криптостойкие. На API границе с пользовательскими данными SipHash оставляют.

```rust
use std::collections::HashMap;
use ahash::RandomState;

fn main() {
    let mut m: HashMap<u64, u64, RandomState> = HashMap::default();
    for i in 0..100 { m.insert(i, i * i); }
    println!("{}", m[&5]);
}
```

Выбор хешера это всегда tradeoff между безопасностью и скоростью.

### 85. Что такое branch prediction и как мы можем помочь компилятору

Процессор предсказывает ветвления. Промах стоит десятки циклов. Помогать можно. Через #[cold] на функциях обработки редких случаев. Через likely и unlikely интринзики в std::intrinsics или через crate likely_stable. Через реструктуризацию кода, чтобы горячий путь был прямым, без вложенных match. На уровне выражений match со многими вариантами компилируется в jump table, что обычно лучше длинной цепочки if else.

```rust
fn parse(b: &[u8]) -> Option<u32> {
    if b.is_empty() { return None; }
    let mut acc = 0u32;
    for &c in b {
        if !c.is_ascii_digit() { return None; }
        acc = acc.wrapping_mul(10).wrapping_add((c - b'0') as u32);
    }
    Some(acc)
}
```

Горячая ветка для цифр идет первой и без вложений. Это тот случай, когда читаемость и скорость совпадают.

### 86. Cache friendly код в Rust, как структурировать данные

Локальность данных решает. Vec<T> с маленькими T работает быстрее, чем Vec<Box<T>>, потому что доступ последовательный, без промахов кэша. SoA (struct of arrays) часто быстрее AoS (array of structs), если код одновременно работает только с подмножеством полей. Это типичный паттерн для рантаймов игр и для аналитики. Сами по себе типы вроде SmallVec и tinyvec выигрывают именно на этом, потому что прячут небольшие данные внутри стека.

```rust
struct WorldAoS { items: Vec<(u32, f32, f32)> }
struct WorldSoA { ids: Vec<u32>, x: Vec<f32>, y: Vec<f32> }
```

Если алгоритм гоняет по x и y и не трогает id, SoA попадает в кэш плотнее.

### 87. Что такое monomorphization cost и как с ней жить

Каждый дженерик инстансциируется под конкретный тип. Это раздувает бинарник и время компиляции. На больших проектах это становится заметно. Лекарства. Делить функции на тонкую generic обертку и толстую non generic реализацию, которая принимает &dyn или &str вместо impl Trait. Не делать дженерики там, где достаточно &str или &[u8]. Использовать impl Trait внутри функций, а не на API границе, если не нужна гибкость.

```rust
fn log_inner(s: &str) { println!("{}", s); }
pub fn log<T: AsRef<str>>(s: T) { log_inner(s.as_ref()); }
```

Генерик мономорфизируется в тонкую функцию, которая просто зовет общую log_inner. Бинарник растет минимально.

### 88. PGO и LTO, что это и стоит ли включать

LTO это link time optimization, она позволяет инлайнить и оптимизировать через границы крейтов. Включается в Cargo.toml профиле release. Дает обычно 5 15 процентов скорости и заметно более долгий линк. Thin LTO быстрее, fat LTO медленнее, но иногда чуть лучше. PGO это profile guided optimization, компилятор использует данные о реальных вызовах для выбора инлайнов и реструктуризации кода. Дает еще 5 20 процентов на хорошо профилируемой рабочей нагрузке. Для серверного кода почти всегда оправдано.

```toml
[profile.release]
lto = "fat"
codegen-units = 1
```

codegen-units = 1 ограничивает параллелизм компиляции, но дает компилятору больше контекста для оптимизаций.

### 89. Profile guided optimization и benchmarks с criterion

Criterion это de facto стандарт микробенчмарков в Rust. Запускает функцию много раз, выкидывает выбросы, считает доверительные интервалы. Главное при бенчинге это правильно сравнивать релизный билд с тем же набором фич. Microbench легко обмануть себя, если не позаботиться о black_box, который мешает компилятору соптимизировать вычисление до константы.

```rust
use criterion::{black_box, criterion_group, criterion_main, Criterion};

fn sum_to(n: u64) -> u64 { (1..=n).sum() }

fn bench(c: &mut Criterion) {
    c.bench_function("sum_to_1000", |b| b.iter(|| sum_to(black_box(1000))));
}

criterion_group!(benches, bench);
criterion_main!(benches);
```

bench запускается через cargo bench. Результаты сохраняются и сравниваются между прогонами.

## Макросы и метапрограммирование

### 90. Декларативные макросы macro_rules, базовые принципы

Декларативный макрос задается через macro_rules. У него есть набор правил matcher to transcriber, где matcher описывает синтаксис, а transcriber генерирует код. Используются фрагменты expr, ident, ty, tt и другие. Это безопасный способ генерировать код, который виден в синтаксическом дереве до тайпчека. Подходит для DSL, для упрощения повторяющегося кода, для конструкторов коллекций.

```rust
macro_rules! hashmap {
    ($($k:expr => $v:expr),* $(,)?) => {{
        let mut m = std::collections::HashMap::new();
        $( m.insert($k, $v); )*
        m
    }};
}

fn main() {
    let m = hashmap! { "a" => 1, "b" => 2 };
    println!("{:?}", m);
}
```

Это типовой паттерн. Если в проекте появилось много повторяющихся инициализаций, такой макрос обычно оправдан.

### 91. Гигиена макросов, что это и какие у нее границы

Гигиена это свойство макроса не путать свои идентификаторы с пользовательскими. Декларативные макросы Rust в основном гигиеничны для локальных имен. Это значит, что let x = 5 внутри макроса не перекрывает x в вызывающем контексте. Полной гигиены для всех видов имен пока нет, особенно для типов и трейтов. Поэтому в макросах безопаснее писать $crate::path::to::Item вместо просто Item.

```rust
macro_rules! once {
    () => { let x = 1; let _ = x; };
}

fn main() {
    let x = 10;
    once!();
    println!("{}", x); // 10, не перекрыто
}
```

Эта гигиена убирает целый класс багов, которые были типичны для макросов в C.

### 92. Процедурные макросы, три вида

Есть три вида proc macros. Function like, которые вызываются как make_thing!. Derive макросы, которые вешаются на структуру через #[derive(Foo)]. Attribute макросы, которые модифицируют элемент через #[my_attr]. Под капотом все три получают TokenStream и возвращают TokenStream. Для разбора используют syn, для генерации quote, для отображения ошибок proc-macro-error.

```rust
// Cargo.toml: [lib] proc-macro = true
// use proc_macro::TokenStream;
// use quote::quote;
// #[proc_macro_derive(Hello)]
// pub fn hello(input: TokenStream) -> TokenStream {
//     let ast: syn::DeriveInput = syn::parse(input).unwrap();
//     let name = &ast.ident;
//     quote! { impl #name { fn hello() { println!("hello from {}", stringify!(#name)); } } }.into()
// }
```

Proc макросы это полный Rust компилятор как зависимость, поэтому увеличивают время сборки. Применять стоит, когда декларативных макросов уже не хватает.

### 93. Build script build.rs, типичные применения

build.rs запускается перед сборкой crate. Используется для генерации кода, для подключения C библиотек через cc, для проверки фич окружения, для генерации констант на основе git. Общается с cargo через печать строк cargo:rerun-if-changed=, cargo:rustc-cfg=, cargo:warning=. В большом проекте build.rs часто становится точкой, где собирают protobuf, capnproto, flatbuffers схемы и кладут результаты в OUT_DIR.

```rust
// build.rs
fn main() {
    println!("cargo:rerun-if-changed=schema.proto");
    println!("cargo:rustc-env=BUILD_VERSION=1.0.0");
}
```

Generated файлы потом подключают через include!(concat!(env!("OUT_DIR"), "/schema.rs")).

### 94. Что такое const fn и какие у нее ограничения

const fn это функция, которая может быть вычислена в compile time. Применяется для создания констант, для размеров массивов, для логики, которую хочется проверять статически. Ограничения медленно ослабляются. Раньше нельзя было if внутри const fn, теперь можно. Многие методы стандартной библиотеки уже const. Аллокации в const fn пока ограничены, циклы разрешены.

```rust
const fn square(n: u32) -> u32 { n * n }

const N: u32 = square(7);
static ARR: [u8; square(2) as usize] = [0; 4];

fn main() { println!("{} {}", N, ARR.len()); }
```

const fn полезен в библиотечном коде. Конфигурация и константы становятся вычислимыми, и тип системе доступно больше информации.

### 95. Что такое typestate и как он реализуется в Rust

Typestate это паттерн, при котором состояние объекта закодировано в его типе. Невозможные переходы не компилируются. Реализуется через generic параметры, fantom типы и trait bounds. Очень часто встречается в API сетевых протоколов и парсеров. Builder тоже это разновидность typestate, когда обязательные поля проверяются типом возвращаемого значения.

```rust
struct Open; struct Closed;
struct Socket<S> { _s: std::marker::PhantomData<S> }

impl Socket<Closed> { fn open(self) -> Socket<Open> { Socket { _s: std::marker::PhantomData } } }
impl Socket<Open> { fn close(self) -> Socket<Closed> { Socket { _s: std::marker::PhantomData } } }

fn main() {
    let s = Socket::<Closed> { _s: std::marker::PhantomData };
    let o = s.open();
    // o.open(); // ошибка, у Open нет open
    let _ = o.close();
}
```

Компилятор не даст вызвать open на уже открытом сокете. Это бесплатный рантайм инвариант.

### 96. Builder pattern в Rust, как делать правильно

Builder используется, когда у структуры много полей, часть из которых опциональна. В Rust типовая реализация это отдельный билдер тип с методами с цепочечным возвратом self или &mut self. Для обязательных полей часто используется typestate, тогда build не скомпилируется без них. Альтернативно, build возвращает Result с описанием отсутствующего поля. Первый вариант жестче, второй гибче.

```rust
struct Client { url: String, timeout_ms: u32 }

struct ClientBuilder { url: Option<String>, timeout_ms: u32 }

impl ClientBuilder {
    fn new() -> Self { Self { url: None, timeout_ms: 1000 } }
    fn url(mut self, u: impl Into<String>) -> Self { self.url = Some(u.into()); self }
    fn timeout_ms(mut self, t: u32) -> Self { self.timeout_ms = t; self }
    fn build(self) -> Result<Client, &'static str> {
        Ok(Client { url: self.url.ok_or("url required")?, timeout_ms: self.timeout_ms })
    }
}

fn main() {
    let _c = ClientBuilder::new().url("http://x").timeout_ms(500).build().unwrap();
}
```

Для сложного API правильный builder сильно повышает читаемость вызовов.

### 97. Error handling, anyhow и thiserror, когда что

thiserror используется для библиотечных ошибок. Дает derive для enum, который реализует std::error::Error с источниками и сообщениями. anyhow используется в приложениях, где нужно собирать ошибки из разных источников в один опрозрачный тип с контекстом. Правило большого пальца. Внутри библиотеки thiserror и осмысленные enum. На уровне main и интеграционных слоев anyhow и контекст.

```rust
use thiserror::Error;

#[derive(Error, Debug)]
enum StoreError {
    #[error("io: {0}")]
    Io(#[from] std::io::Error),
    #[error("missing key {0}")]
    Missing(String),
}

fn load(path: &str) -> Result<String, StoreError> {
    Ok(std::fs::read_to_string(path)?)
}
```

Вызывающий код получает четкий enum и может матчить на конкретные варианты, а не разбирать строку.

### 98. Дизайн API на трейтах, что отдавать наружу

Хороший публичный API скрывает реализацию и фиксирует контракт. На практике это значит. Возвращать impl Trait вместо конкретных типов, чтобы не закладываться на детали. Принимать impl IntoIterator или impl AsRef, чтобы не заставлять пользователя конвертировать. Не светить дженерики, которые нужны только внутри. Делать новые методы по необходимости, не превращать трейты в свалку. Чем меньше у трейта методов, тем легче его реализовать сторонним типам.

```rust
pub trait KV {
    fn get(&self, key: &str) -> Option<String>;
    fn put(&mut self, key: &str, value: &str);
}
```

Комментарий. Минимальный набор методов, никаких лишних дженериков, легко мокать в тестах.

### 99. Versioning, semver и breaking changes в Rust

Rust crates следуют semver. Patch это совместимые исправления, minor добавление API без поломок, major breaking changes. Что считается breaking. Удаление публичного элемента, изменение сигнатуры, переименование, новые обязательные методы в pub трейте, новые обязательные generic параметры. Что не breaking. Новые public функции, новые варианты в #[non_exhaustive] enum, добавление #[must_use]. Чтобы спокойно менять enum в будущем, его помечают non_exhaustive еще в первой версии.

```rust
#[non_exhaustive]
pub enum Event { Connected, Disconnected }
```

Теперь добавление третьего варианта в minor релизе не сломает пользователей.

### 100. Безопасный multi crate workspace, как организовать большой проект

Для проекта, который перерос один crate, типичная структура это cargo workspace с несколькими членами. Например, core содержит чистую логику без IO. db содержит работу с хранилищем. http содержит транспорт. bin собирается из них и не содержит логики. Это дает понятные границы зависимостей, ускоряет инкрементальную сборку и упрощает тестирование. Внутри workspace полезны общие dependencies в workspace.dependencies, чтобы версии не разъезжались.

```toml
[workspace]
members = ["core", "db", "http", "bin"]

[workspace.dependencies]
serde = { version = "1", features = ["derive"] }
tokio = { version = "1", features = ["full"] }
```

Из практики. Чем чище разделены крейты по обязанностям, тем проще менять одно, не задевая другое. Это главный практический выигрыш Rust workspace.
