# Разбор 100 вопросов с собеседований по Rust

Подробные ответы с упором на практику: что компилятор делает на самом деле, где наивный путь приводит к UB, какие подводные камни встречаются в продакшене. Привожу примеры кода, ссылки на конкретные API и типичные ошибки.

## Владение, заимствование, лайфтаймы

### 1. Move-семантика и отличие от копирования в C++

В Rust присваивание `let b = a;` для типа без `Copy` физически перемещает значение: исходная переменная `a` становится недоступной (move out), компилятор отслеживает это статически и запрещает дальнейшее использование. Под капотом для большинства типов move это побайтовое копирование (`memcpy`), но семантически после него прежнее место считается «опустошённым» и не дропается. В C++ move реализован библиотечно через rvalue-ссылки и `std::move`: исходный объект остаётся в валидном, но неопределённом состоянии, и его деструктор всё равно вызовется. В Rust деструктор у moved-from переменной не запускается, потому что владелец сменился. Практический эффект: можно безопасно отдать `File` или `Mutex` в другой поток, не боясь, что закроется FD или разблокируется мьютекс дважды.

### 2. Когда тип реализует `Copy` автоматически

`Copy` — это маркерный трейт, и автоматически он не реализуется никогда: всегда нужен явный `#[derive(Copy, Clone)]` или `impl Copy for T`. Компилятор разрешает дерайвить `Copy` только если все поля `Copy`, тип не реализует `Drop` и не содержит `UnsafeCell` напрямую. `String` не `Copy`, потому что владеет хипом: побитовое копирование указателя привело бы к двойному `free` при дропе. То же касается `Vec<T>`, `Box<T>`, `Rc<T>` (там ещё счётчик ссылок). Практический совет: не делайте `Copy` для типов больше 16-32 байт — копирование станет дороже, чем move через ссылку, и это размажется по бенчмаркам незаметно.

### 3. Правило aliasing XOR mutability

Borrow checker гарантирует: в каждый момент либо одна `&mut T`, либо любое число `&T`, но не оба сразу. Это даёт две вещи. Во-первых, исключает data race на однопоточном уровне (модификация во время чтения). Во-вторых, открывает оптимизации уровня LLVM `noalias`: компилятор знает, что через `&mut` никто другой не подсматривает, и может свободно кешировать значение в регистре. Практическая боль: итерация по `Vec` с одновременной модификацией. Решения — собрать индексы заранее, использовать `Vec::retain`, `drain_filter`, или индексировать вручную через диапазон `0..len`. Для графов и связных структур обычно переходят на `Vec<Node>` с индексами вместо `Rc<RefCell<Node>>`.

### 4. NLL и старая модель лайфтаймов

До NLL лайфтайм заимствования тянулся до конца лексической области видимости. Код `let mut v = vec![1]; let r = &v[0]; v.push(2);` падал, даже если `r` дальше не использовался. NLL (стабилизирован в 2018 edition) делает лайфтайм заимствования равным интервалу между его созданием и последним использованием. После NLL компилятор смотрит на CFG (control flow graph) и видит, что `r` мёртв к моменту `push`. Дальше развилось ещё в Polonius (на nightly) — он решает оставшиеся редкие ложноположительные ошибки, особенно с условными возвратами ссылок из функций. На практике NLL убрал 80% «зачем тут `{ ... }`-блок» хаков из старого кода.

### 5. Зачем явные лайфтаймы в сигнатурах

Компилятор выводит лайфтаймы только внутри тела функции. В сигнатуре он не угадывает, какая ссылка к какой относится, потому что сигнатура — это публичный контракт: меняя её, вы меняете семантику для всех вызывающих. Например, `fn longest(x: &str, y: &str) -> &str` неоднозначна: вернётся ли ссылка с лайфтаймом `x` или `y`. Явно написав `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str`, мы зафиксировали: результат живёт не дольше, чем меньший из двух аргументов. Если хочется, чтобы результат был связан только с одним из аргументов, ставим разные лайфтаймы: `fn first<'a, 'b>(x: &'a str, _y: &'b str) -> &'a str`.

### 6. `&'a T` vs `&'static T`

`'a` — это параметр, конкретный регион времени жизни, который выводится в точке вызова. `'static` — особый лайфтайм, означающий «живёт до конца программы». Тонкость: `T: 'static` не означает, что значение существует с момента запуска. Это означает, что значение не содержит никаких заимствований с более коротким лайфтаймом. `String`, созданный в рантайме, удовлетворяет `T: 'static`, потому что он владеет своими данными и не зависит от внешних ссылок. Поэтому `tokio::spawn` требует `F: 'static` — не «вечной жизни», а отсутствия висячих ссылок наружу. Литералы строк `"hello"` имеют тип `&'static str`, потому что лежат в `.rodata` бинарника.

### 7. Lifetime elision rules

Три правила, по которым компилятор расставляет лайфтаймы в `fn`:
- каждый входной `&` или `&mut` получает свой собственный лайфтайм,
- если входной лайфтайм один, он назначается всем выходным,
- если у функции есть `&self` или `&mut self`, лайфтайм `self` назначается всем выходным.

Не работает при двух и более входных ссылках без `self` — придётся писать руками. Также не работает для замыканий: там тип `Fn(&str) -> &str` ведёт себя как HRTB `for<'a> Fn(&'a str) -> &'a str`, но если хочется других связей, придётся писать через явный трейт.

### 8. Variance: covariant, contravariant, invariant

Variance отвечает на вопрос: если `'a: 'b` (то есть `'a` живёт не меньше `'b`), что с `F<'a>` и `F<'b>`. `&'a T` ковариантна по `'a` и по `T`: длинный лайфтайм можно сократить, как и `&'static str` использовать там, где ждут `&'a str`. `&'a mut T` ковариантна по `'a`, но инвариантна по `T`: иначе можно было бы записать в место короткой ссылки длинную, а потом прочитать её обратно как длинную. `fn(T)` контравариантна по `T`: функция, принимающая `Animal`, годится туда, где ждут принимающую `Cat`. Практика: variance объясняет, почему `Vec<&'static str>` нельзя присвоить переменной типа `Vec<&'a str>` напрямую — `Vec` инвариантен по `T` через `UnsafeCell`-подобную семантику владения.

### 9. Почему `Cell<T>` инвариантен по `T`

`Cell` позволяет мутировать содержимое через `&Cell<T>`. Если бы он был ковариантен и `T = &'long str`, можно было бы получить `&Cell<&'short str>` через подтип, записать туда короткую ссылку, а потом прочитать как длинную и use-after-free. Поэтому `Cell` (и `RefCell`, `UnsafeCell`) делают инвариантными через `PhantomData<fn(T) -> T>` или встроенный `UnsafeCell`. Это общее правило: всё, что хранит `T` за внутренней мутабельностью, должно быть инвариантно по `T`.

### 10. Возврат ссылки на локальную переменную

`fn foo() -> &i32 { let x = 5; &x }` не компилируется: `x` дропается при выходе из функции, ссылка повисла бы. Borrow checker ловит это через анализ лайфтаймов: у `x` лайфтайм короче, чем у предполагаемого выходного, противоречие. Workaround: вернуть `Box<i32>`, `String` или другой owned-тип. Если хочется именно ссылку — её должен предоставить вызывающий: `fn foo(buf: &mut i32) -> &mut i32`. На уровне дизайна это сигнал, что владение должно подняться вверх по стеку.

### 11. Self-referential структуры

Нельзя написать `struct Foo { data: String, slice: &str }` со ссылкой на собственное поле: при move структуры адрес `data` изменится, а `slice` останется указывать на старое место. Решений несколько:
- `Pin` + `!Unpin` маркер, чтобы зафиксировать в памяти, плюс unsafe для построения,
- крейт `ouroboros` — макрос, который генерирует безопасный API,
- хранить индексы или диапазоны `Range<usize>` вместо ссылок,
- `Rc`/`Arc` для разделяемого владения, тогда «ссылка» — это `Rc`-клон.

Async-блоки решают эту проблему встроенно: компилятор сам пинит state machine, в которую могут попадать ссылки на её же поля.

### 12. `PhantomData` и зачем он нужен

`PhantomData<T>` — zero-sized тип, который говорит компилятору: «эта структура ведёт себя так, будто содержит `T`, хоть его и нет в полях». Применения: фиксировать variance (`PhantomData<fn(T) -> T>` для инвариантности), помечать ownership (`PhantomData<T>` влияет на dropck — компилятор будет считать, что `T` дропается при дропе вашей структуры), задавать типажные параметры для FFI-обёрток. Классический пример — `struct Slice<'a, T> { ptr: *const T, len: usize, _marker: PhantomData<&'a T> }`: без маркера лайфтайм `'a` и тип `T` не были бы привязаны к структуре, и компилятор разрешил бы что угодно.

### 13. `Drop` и порядок освобождения

Поля структуры дропаются в порядке объявления (сверху вниз), элементы кортежа — слева направо, элементы массива — от первого к последнему. Локальные переменные в блоке — в обратном порядке объявления (LIFO, как стек). `Drop::drop` вызывается перед дропом полей, не вместо: вы не обязаны вручную дропать поля. Нельзя вызвать `drop` напрямую на `&mut self` — компилятор запретит, и правильно: иначе двойной drop. Если нужно «частично уронить», используйте `ManuallyDrop` и `std::ptr::drop_in_place`. Боль: при панике в середине `Drop` — unwind пройдёт по уже частично дропнутым полям, что обычно безопасно, но если в `Drop` снова паника — программа аварийно завершается через `abort`.

### 14. Drop check (dropck)

Проверка, что в `Drop::drop(&mut self)` мы не обратимся к уже умершим заимствованиям. Например, `struct Foo<'a> { r: &'a str }` с реализацией `Drop` не может дропнуться после того, как `'a` истечёт: dropck заставит `'a` пережить дроп `Foo`. Атрибут `#[may_dangle]` (unsafe-фича для библиотек вроде `Vec`, `Box`) ослабляет это: `Vec<T>` обещает, что в `Drop` не трогает `T` через ссылки, только дропает его. Без этого `Vec<&'a str>` не смог бы существовать с не-`'static` лайфтаймом, потому что dropck требовал бы `'a` пережить весь блок.

### 15. Interior mutability: Cell, RefCell, UnsafeCell

`UnsafeCell<T>` — единственный примитив в языке, позволяющий мутировать значение через `&`. Всё остальное построено над ним. `Cell<T>` — для типов `Copy` или `replace`-семантики: можно получить значение копированием или поменять местами, но не получить `&mut` на содержимое. Не требует рантайм-проверок, бесплатна. `RefCell<T>` — даёт `borrow()` и `borrow_mut()` с runtime-проверкой: при нарушении aliasing XOR mutability — паника. Дороже, но даёт `&` и `&mut` на содержимое. `Mutex`/`RwLock` — те же идеи, но для многопоточности с блокировкой. Правило: `Cell` для счётчиков и флагов, `RefCell` когда нужно `&mut` без `mut` снаружи (например, lazy-инициализация поля), `Mutex` когда между потоками.

## Типы, трейты, обобщения

### 16. `impl Trait` в аргументе и в возврате

В аргументе `fn foo(x: impl Iterator<Item = i32>)` — синтаксический сахар для `fn foo<T: Iterator<Item = i32>>(x: T)`. Полный универсальный тип, монорфизируется для каждого конкретного `T`. В возврате `fn make() -> impl Iterator<Item = i32>` — это existential type: возвращается какой-то конкретный тип, известный компилятору, но скрытый от вызывающего. Это позволяет возвращать невыразимые типы (замыкания, цепочки итераторов вроде `Filter<Map<...>>`), не указывая их явно. Ограничения: нельзя возвращать разные конкретные типы из разных веток (`if cond { iter1 } else { iter2 }` упадёт, если `iter1` и `iter2` разной структуры — здесь нужен `Box<dyn Iterator>`). В трейтах `impl Trait` в возврате (RPITIT) стабилизирован в 1.75.

### 17. `dyn Trait` и fat pointer

`Box<dyn Trait>` или `&dyn Trait` — это «толстый указатель»: 16 байт на 64-bit платформе, два слова. Первое — указатель на данные, второе — на vtable. Vtable содержит указатели на методы, размер, alignment, drop. Вызов метода через `dyn` — это разыменование vtable плюс косвенный вызов, что мешает инлайнингу. На горячем пути overhead заметен (10-30%), на холодном — невидим. Плюсы: один и тот же код работает с разными типами, бинарник не раздувается монорфизацией. Используют для гетерогенных коллекций (`Vec<Box<dyn Handler>>`), плагинов, эррор-типов (`Box<dyn Error>`).

### 18. Объектная безопасность трейта

Трейт объектно-безопасен, если по нему можно построить vtable. Правила:
- никакой `Self: Sized` (явно или неявно через `Sized` bound),
- методы не возвращают `Self` (откуда взять размер?),
- методы не используют generic параметры в сигнатуре (для каждой инстанциации нужна своя строчка в vtable),
- нет ассоциированных констант (на nightly уже частично разрешено).

Воркэраунды: метод с `Self: Sized` исключается из vtable, его нельзя вызвать через `dyn`, но он не ломает объектность. Дженерик-методы заменяют на `&dyn Trait` параметром. `Self` в возврате заменяют на `Box<Self>` или `Box<dyn Trait>`.

### 19. Associated types vs generic params

`trait Iterator { type Item; fn next(&mut self) -> Option<Self::Item>; }` — `Item` ассоциированный, один тип на одну реализацию. У `Vec<i32>::IntoIter` всегда `Item = i32`. `trait From<T> { fn from(t: T) -> Self; }` — `T` дженерик, один тип может реализовать `From<i32>` и `From<String>` одновременно. Правило: если для конкретного `Self` тип определяется однозначно, делайте associated. Если хочется множественных реализаций для разных входов — generic. `Iterator` сделан associated, потому что один итератор итерирует один тип элементов, и это упрощает вывод типов в `.collect()`.

### 20. GAT и lending iterator

Generic Associated Types позволяют ассоциированному типу принимать параметры, в том числе лайфтаймы. Классическая проблема — `Iterator`, который отдаёт ссылки на свои внутренности (lending iterator):

```rust
trait LendingIterator {
    type Item<'a> where Self: 'a;
    fn next(&mut self) -> Option<Self::Item<'_>>;
}
```

Это позволяет, например, итератору окон по `&mut [T]` отдавать `&mut [T]` без двойного заимствования. Стандартный `Iterator` так не умеет, потому что `Item` фиксирован и не может зависеть от лайфтайма `&mut self`.

### 21. Orphan rule

Реализовать трейт `Trait for Type` можно только если либо трейт, либо тип определены в текущем крейте. Иначе два разных крейта могли бы независимо реализовать `Display for Vec<i32>` по-разному, и при подключении обоих случилась бы катастрофа линковщика. Обходы: newtype (`struct MyVec(Vec<i32>); impl Display for MyVec`), либо контрибьютить в исходный крейт. Существует расширение `fundamental` атрибут на типах вроде `Box` и `&` — для них правило слегка ослаблено, чтобы `impl Foo for &MyType` работал у пользователя.

### 22. Newtype pattern

`struct Meters(f64);` оборачивает примитив, чтобы дать ему имя в системе типов и не путать с `Seconds(f64)`. Применения: type-safe единицы измерения, sealed-обёртки над данными из БД (`UserId(u64)` не присвоится `PostId(u64)`), реализация чужих трейтов на чужих типах в обход orphan rule, скрытие деталей внешнего API. Стоимость нулевая благодаря `#[repr(transparent)]` и оптимизатору. Минус: придётся вручную прокидывать методы через `Deref` или явно. Для `Deref` есть оговорки (см. вопрос 24).

### 23. `From`, `Into`, `TryFrom`, `AsRef`, `Borrow`, `Deref`

`From<T> for U` — инфаллибельная конверсия, владение перетекает. `Into` выводится автоматически из `From`, обычно реализуют `From`. `TryFrom` — версия с `Result` для случаев, когда конверсия может провалиться (число не влезло, строка не распарсилась). `AsRef<T>` — дешёвая ссылочная конверсия, например `String: AsRef<str>`, `PathBuf: AsRef<Path>`. Идеально для аргументов функций: `fn foo(p: impl AsRef<Path>)`. `Borrow<T>` похож на `AsRef`, но с дополнительным контрактом: `Hash`, `Eq`, `Ord` должны совпадать с целевыми. Поэтому `HashMap::get` принимает `&Q where K: Borrow<Q>`. `Deref` — для умных указателей: `Box<T>: Deref<Target = T>`, позволяет автодереференс и method call lookup проходить сквозь обёртку.

### 24. Когда реализовывать `Deref`

Правильно: для умных указателей, которые семантически «являются» содержимым (`Box`, `Arc`, `Rc`, `MutexGuard`, `String -> str`). Антипаттерн: `Deref` от `MyStruct` к `InnerStruct` ради наследования методов. Это ломает читаемость (методы появляются как из ниоткуда), создаёт неожиданные конверсии в generic-функциях, путает рефакторинг. Clippy ругается на это правилом `deref_addrof` и `explicit_auto_deref`. Альтернатива: реализуйте `AsRef` или явные методы-делегаты. Особенно опасно для типов, инкапсулирующих инварианты: `Deref` даёт `&Inner`, через который можно обойти валидацию.

### 25. Coherence

Coherence — это глобальная гарантия, что у пары (trait, type) есть максимум одна реализация во всём графе зависимостей. Orphan rule — её локальная часть. Компилятор отказывает в `impl Foo for T` где-нибудь, потому что upstream-крейт может добавить эту реализацию в новой версии, и ваш код сломается. Это объясняет странные ограничения вроде «нельзя impl From<MyType> for Vec<T>», потому что `Vec<T>` — это `std`-тип. Negative reasoning тоже не работает: нельзя сказать `impl Foo for T where T: !Bar`. Поэтому specialization до сих пор не стабилизирована — она ломает coherence в нетривиальных случаях.

### 26. Blanket impl без конфликта с конкретными

`impl<T: Display> MyTrait for T { ... }` блокирует `impl MyTrait for SpecificType` — компилятор посчитает это перекрытием. Решения: разделить трейт на два (общий и специальный) и реализовать раздельно; использовать marker-трейт чтобы сузить blanket; на nightly — `#[feature(specialization)]`. На практике обычно делают так: `impl<T> MyTrait for T where T: Display + NotMySpecial` через маркерный трейт, либо просто описывают через enum.

### 27. `Sized`, `?Sized`, DST

По умолчанию все generic параметры неявно ограничены `Sized`. `?Sized` снимает это ограничение, разрешая DST (dynamically sized types) — `str`, `[T]`, `dyn Trait`. Их нельзя положить на стек или передать по значению, только за указателем (`&str`, `Box<dyn Trait>`). `!Sized` существует, но используется редко. Практика: если ваша функция работает с `&T`, добавляйте `T: ?Sized` — это сделает её применимой к `&str` и `&dyn Trait`:

```rust
fn print<T: Display + ?Sized>(x: &T) { println!("{}", x); }
```

### 28. Specialization

Фича позволяет писать `default impl` для общего случая и более специальный — для конкретного. Не стабилизирована, потому что в текущей реализации позволяет писать unsound-код: специализация может зависеть от лайфтаймов, а лайфтаймы стираются в кодгене, и это создаёт несоответствие. Есть min_specialization (более узкий вариант) — используется внутри std для оптимизаций (`Vec::extend` для `Copy`-типов работает через `memcpy`). В user-code обычно эмулируют через autoref/autoderef-трюки или через GAT.

### 29. Higher-ranked trait bounds

`for<'a> Fn(&'a str) -> &'a str` означает: функция работает для любого лайфтайма `'a`, выбираемого вызывающим. Без `for<'a>` лайфтайм фиксировался бы в точке определения, и замыкание `|s| s` не подходило бы под `fn(&str) -> &str` универсально. HRTB критичен для замыканий, которые принимают ссылки из неизвестного источника. Например, `fn apply<F: for<'a> Fn(&'a str) -> &'a str>(f: F, s: &str) -> &str`. Без HRTB пришлось бы прокидывать лайфтайм через всю сигнатуру.

### 30. `Fn`, `FnMut`, `FnOnce`

`FnOnce` — самый общий: может потреблять захваченные переменные, вызывается один раз (`self`). `FnMut` — может мутировать захваты (`&mut self`). `Fn` — только читает (`&self`). Иерархия: `Fn: FnMut: FnOnce`. Компилятор реализует самый сильный возможный трейт. Замыкание `|x| x + counter` где `counter: i32` реализует `Fn`, потому что копирует. `|x| { *counter += x; *counter }` где `counter: &mut i32` — `FnMut`. `move |x| { drop(s); x }` где `s: String` — `FnOnce`, потому что `drop` потребляет. Практика: API принимает самый общий, который ему подходит. Если хватит одного вызова — `FnOnce`, в горячем цикле — `Fn`.

## Конкурентность и параллелизм

### 31. `Send` и `Sync`, почему `Rc` ни тот ни другой

`Send` — тип можно переместить в другой поток. `Sync` — на тип можно дать ссылку `&T` из нескольких потоков (то есть `&T: Send`). Оба — auto-traits, реализуются автоматически, если все поля реализуют. `Rc<T>` не `Send`, потому что счётчик ссылок не атомарный: одновременный клон из двух потоков приведёт к гонке и UAF. Соответственно не `Sync`: иначе через `&Rc` можно было бы клонировать из другого потока. `Arc<T>` использует `AtomicUsize` для счётчика и потому `Send + Sync` при `T: Send + Sync`. `Cell<T>` и `RefCell<T>` не `Sync`, потому что их мутация не атомарна.

### 32. `Mutex<T>: Send/Sync` правила

`Mutex<T>: Send when T: Send` — отправить мьютекс в другой поток можно, если содержимое можно отправить. `Mutex<T>: Sync when T: Send` (заметьте, именно `Send`, не `Sync`!) — потому что `&Mutex<T>` позволяет получить `&mut T` через `lock()`, а это эквивалентно отправке `T` в поток, который держит `lock`. Поэтому `Mutex<Rc<...>>` не `Sync`. Практика: если вам нужно делиться `!Send` значением между потоками — вы что-то спроектировали не так, перепроверьте.

### 33. Memory ordering

`Relaxed` — никаких гарантий упорядочивания между потоками, только атомарность самой операции. Для счётчиков статистики, где порядок не важен. `Release` на write — все предыдущие записи этого потока становятся видны после `Acquire`-чтения этой же ячейки другим потоком. Классика — публикация инициализированных данных через флаг. `Acquire` на read — все последующие чтения видят то, что было записано до `Release`. `AcqRel` — для read-modify-write операций (CAS, fetch_add): одновременно `Acquire` для чтения и `Release` для записи. `SeqCst` — самый сильный, добавляет глобальный тотальный порядок между всеми SeqCst-операциями. Стоит дороже из-за барьеров (на x86 ~30 циклов на `mfence`, на ARM ещё дороже).

### 34. Опасность `Relaxed` для синхронизации

Классическая ошибка: поток A пишет `data = 42`, потом `ready.store(true, Relaxed)`. Поток B читает `ready.load(Relaxed)`, видит `true`, читает `data`. На x86 это случайно может работать (сильная модель памяти), на ARM/RISC-V — нет: `data` ещё не доехала до кеша B. Правильно — `Release` на write и `Acquire` на read, тогда между ними устанавливается happens-before. Прогон под `loom` на нетривиальной модели быстро вскроет проблему.

### 35. ABA-проблема

Поток A читает указатель `P1`, готовится сделать CAS. Поток B освобождает `P1`, аллоцирует `P2` (вдруг по тому же адресу), потом ещё раз освобождает и снова аллоцирует `P1`. A делает CAS, видит «тот же» указатель, успешно меняет — а содержимое уже совсем другое. Защиты: тегированные указатели (`AtomicU64` со счётчиком в верхних битах), hazard pointers, эпохальная реклеймация (`crossbeam_epoch`). Стандартная библиотека Rust в lock-free контейнерах эту проблему обходит, потому что `Arc` владеет данными, а `Drop` контролируется счётчиком — но при ручной работе с указателями ABA — главный враг.

### 36. Poisoning у `Mutex`

Если поток держит `MutexGuard` и паникует, мьютекс «отравляется»: следующий `lock()` вернёт `Err(PoisonError)`. Обычно достают данные через `.into_inner()` или `PoisonError::into_inner()`, потому что состояние может быть невалидным. На практике многие приложения логируют и продолжают, потому что инвариант сохраняется. `parking_lot::Mutex` не имеет poisoning — там паника не помечает мьютекс, и многие выбирают его именно за это. Если у вас сложный инвариант, который ломается при панике в середине — обязательно либо `std::Mutex` с проверкой, либо ручная защита.

### 37. `RwLock` vs `Mutex`

`RwLock` позволяет много читателей или одного писателя. Кажется выгодным, но: внутри он сложнее, чем `Mutex`, его `read`/`write` дороже (несколько атомарных операций вместо одной), и при высокой конкуренции писатели могут голодать. На coloumns-heavy workload (много чтения, мало записи) выигрыш есть, но обычно меньше ожидаемого. `parking_lot::RwLock` лучше стандартного по производительности и предсказуемости. Если чтения короткие и быстрые, часто `Mutex` побеждает `RwLock` за счёт меньшего оверхеда на саму блокировку.

### 38. `parking_lot::Mutex`

Преимущества: меньше памяти (1 байт против 40+ у std), быстрее в неспорной ситуации (один `compare_exchange` без syscall), не имеет poisoning. На горячем lock-unlock в одном потоке выигрыш 2-3x. Под высокой конкуренцией использует параллельный паркинг (futex-подобный механизм через таблицу), что снижает контеншн на самом мьютексе. Минус: с 1.62 `std::Mutex` на Linux тоже использует futex и стал заметно быстрее. Если новый код — берите `parking_lot` ради API (`if let Some(g) = m.try_lock()` без `Result`-обёртки).

### 39. Spinlock на `AtomicBool`

```rust
while lock.compare_exchange_weak(false, true, Acquire, Relaxed).is_err() {
    std::hint::spin_loop();
}
```

`compare_exchange_weak` дешевле на ARM (LL/SC), `spin_loop` подсказывает CPU включить power-saving и hyperthread yield. Допустимо: очень короткая критическая секция (десятки циклов), нет ОС-потоков на этом ядре с приоритетом ниже. Недопустимо: длинные секции (тратит CPU), однопроцессорная система (тогда вы блокируете того, кто должен освободить). В пользовательском коде обычно лучше `Mutex` — он умный, при контеншне уйдёт в futex.

### 40. False sharing

Два потока пишут в разные `AtomicU64`, лежащие в одной кеш-линии (64 байта обычно). Каждая запись инвалидирует линию у другого ядра, кеш гоняется туда-сюда — производительность падает в 10-100 раз. Решение: `#[repr(align(64))]` или `crossbeam_utils::CachePadded<T>`, которая обёртывает в выровненный нулём паддинг. Особенно важно для счётчиков воркеров, sharded-структур, lock-free очередей. Проверка: `perf stat -e cache-misses` покажет аномально высокий L1d miss rate.

### 41. `crossbeam::epoch`

Reclaim памяти в lock-free структурах: нельзя сразу `free` ноду, на которую может быть указатель у другого потока. Эпохи делят время на интервалы. Поток, входя в критическую секцию, объявляет текущую эпоху. Удалённые ноды кладутся в garbage-список с эпохой удаления. Когда все потоки прошли через две эпохи после удаления, мусор можно безопасно дропнуть — никто на него больше не указывает. Альтернативы: hazard pointers (per-pointer, не per-epoch), RCU (для read-mostly). На практике `crossbeam-epoch` имеет небольшой накладной расход на `pin()` и подходит для большинства случаев.

### 42. `thread::scope` vs `thread::spawn`

`thread::spawn` требует `F: 'static` — потому что поток может пережить родителя, и захваты должны жить вечно. Это запрещает захват ссылок на стек. `thread::scope` (стабилизирован в 1.63) гарантирует, что все spawned-потоки завершатся до выхода из скоупа: можно безопасно одалживать локальные данные:

```rust
let mut data = vec![1, 2, 3];
thread::scope(|s| {
    s.spawn(|| println!("{:?}", &data));
    s.spawn(|| println!("len = {}", data.len()));
});
```

Никаких `Arc`, никаких клонов. Внутри реализовано через `AtomicUsize` счётчик и блокирующее ожидание.

### 43. Передача `!Send` между потоками

Через стандартный `spawn` нельзя. Можно через `channel`, если внутри значение приведено к `Send`-обёртке: например, для `Rc<T>` сначала `Arc::new` и переслать `Arc`, или просто отдать сырой указатель и на принимающей стороне пересобрать. Это unsafe и обычно сигнал плохого дизайна. Иногда легитимно — например, в LocalSet от tokio: `!Send`-future исполняется на одном потоке, но прокладка `Send` нужна для самого LocalSet. В целом: если хочется `!Send` между потоками, лучше переосмыслить владение.

### 44. Каналы: std vs crossbeam vs tokio

`std::sync::mpsc` — историческая многопотребительская очередь (single-consumer), `SyncSender` с лимитом или `Sender` без. Не очень быстрая, нет `select`. `crossbeam::channel` — MPMC, быстрее в разы, поддерживает `select!`, есть bounded/unbounded, поддерживает `recv_timeout`. Стандарт де-факто для синхронного кода. `tokio::sync::mpsc` — async-канал, `send().await` ждёт места в bounded-варианте, `recv().await` ждёт сообщения. Несовместим с блокирующим миром: `tokio::sync::mpsc::Receiver::recv` нельзя вызывать из синхронного кода без рантайма.

### 45. Lazy-инициализация без `lazy_static`

С 1.70 в std есть `OnceLock` и `LazyLock`:

```rust
static CONFIG: LazyLock<Config> = LazyLock::new(|| Config::load());
```

Внутри — атомарный флаг и `Once`. Потокобезопасно, без аллокаций каждый раз. `OnceLock` нужен, если инициализация требует контекста (`set(value)` вызывается явно). Для thread-local есть `thread_local!` макрос. `lazy_static` и `once_cell` теперь архаизмы, хотя `once_cell::sync::OnceCell` имеет немного больше методов.

## Async и runtime

### 46. `Future` и `Pin<&mut Self>`

`Future` — это типаж с одним методом `poll(self: Pin<&mut Self>, cx: &mut Context) -> Poll<Self::Output>`. `Pin` нужен потому, что async-блок компилируется в state machine, поля которой могут ссылаться друг на друга. Если `Future` переместить в памяти между `poll`-ами, внутренние ссылки повиснут. `Pin` гарантирует, что после первого `poll` адрес зафиксирован. Для `Unpin`-типов (большинство простых futures, написанных вручную) это формальность. Для self-referential async-блоков — реальное ограничение.

### 47. Как разворачивается `async fn`

`async fn foo() -> T { ... }` превращается в `fn foo() -> impl Future<Output = T>`. Тело — в анонимный enum (state machine) с состояниями по числу `.await` плюс старт и конец. Каждое `.await` — это `loop { match inner.poll(cx) { Pending => return Pending, Ready(v) => break v } }` с сохранением локальных переменных в поле текущего состояния. Поэтому размер future = размер самого толстого состояния (объединение). Это причина, по которой большие локальные буферы в async-функциях раздувают `spawn`.

### 48. State machine size

Локальные переменные, живущие через `.await`, попадают в state machine. `let buf = [0u8; 4096]; some_future.await; use(&buf);` — `buf` хранится все 4 КБ. Решение: вынести в `Box<[u8]>` (тогда в state machine только указатель), или сузить scope (`{ let buf = ...; use_sync(&buf); }; await;`). Утилита: `cargo +nightly rustc -- -Zprint-type-sizes` показывает размеры всех futures. Tokio документирует, что futures больше ~16 КБ должны быть `Box`-нуты перед `spawn` для уменьшения давления на стек executor-а.

### 49. Зачем `Pin`

`Pin<P>` (где `P: Deref`) — обещание, что после получения `Pin<&mut T>` (или `Pin<Box<T>>`) значение `T` больше не двинется в памяти, пока не дропнется. Это нужно для типов, у которых внутри есть указатели на собственные поля. Без `Pin` любая `mem::swap` или `Vec::push` (с реаллокацией) сломал бы инвариант. `Pin` — это не runtime-проверка, а статический контракт: при `unsafe` создании `Pin` вы клянётесь не двигать.

### 50. `Unpin` vs не-`Pin`

`Unpin` — auto-trait, означает «для меня `Pin` не накладывает реальных ограничений, можно вытащить `&mut T` через `Pin::get_mut`». Большинство типов `Unpin`. `!Unpin` нужен только для self-referential: будущие из `async` блоков с `.await` посередине, генераторы, ручные state machine с внутренними указателями. Чтобы сделать тип `!Unpin`, добавьте поле `PhantomPinned`. После этого `Pin<&mut Self>` будет требовать `unsafe` для разпиновки.

### 51. Self-referential через `Pin`

Без библиотек:
```rust
struct Foo {
    data: String,
    slice: *const str, // или NonNull
    _pin: PhantomPinned,
}
```
Инициализация: создать `data`, потом запиновать (`Box::pin`), потом через `unsafe` поставить `slice = &data[..]`. Дальше методы принимают `Pin<&mut Self>` или `Pin<&Self>`, что гарантирует адрес. На практике используют крейт `pin-project` для безопасной проекции `Pin<&mut Outer> -> Pin<&mut field>` или `&mut field` в зависимости от `#[pin]` атрибута.

### 52. `tokio::spawn` требует `Send + 'static`

`Send` — потому что task может выполниться на любом worker-потоке мультипоточного рантайма (work stealing). `'static` — потому что task живёт неопределённо долго, runtime не знает, когда он завершится, и не может гарантировать, что внешние ссылки доживут. `tokio::task::spawn_local` работает внутри `LocalSet` и привязан к одному потоку, поэтому `Send` не нужен. `'static` всё равно нужен по той же причине. Для скоупа есть экспериментальный `tokio::task::spawn_local_blocking` и сторонние `async-scoped`.

### 53. Cooperative scheduling в tokio

Tokio — это cooperative: задача выполняется до своего следующего `.await`, потом отдаёт управление. Если внутри `async` функции вы делаете `std::thread::sleep` или CPU-heavy цикл без `await`, весь worker блокируется, другие задачи на этом worker не двигаются. На multi-thread runtime work-stealing их перетащит, но если все workers заняты — всё стоит. Tokio начиная с 1.0 добавил budget: после ~128 yield-операций задача принудительно отдаёт управление. Для CPU-bound кода используйте `spawn_blocking` или `rayon`.

### 54. `spawn_blocking`

Запускает синхронный код на отдельном пуле потоков (по умолчанию 512 на multi-thread runtime). Используют для блокирующего IO (старые библиотеки), CPU-тяжёлой работы. Ограничения: пул конечен, при насыщении задачи стоят в очереди. Не передавайте туда async — там нет executor-а. Внутри можно вызвать `tokio::runtime::Handle::current().block_on`, но это легко даёт deadlock. Хороший паттерн: `let r = spawn_blocking(|| heavy()).await?;`.

### 55. `select!`, `join!`, `try_join!`

`join!(a, b)` ждёт оба, возвращает кортеж результатов. `try_join!` — то же, но останавливается при первой ошибке (для `Result`-futures). `select!` — ждёт первый завершившийся, остальные обычно дропаются. `select!` опасен cancellation safety: future, которая дропается на полпути, должна корректно очистить состояние. Не все futures cancel-safe (`tokio::io::AsyncReadExt::read` — да, но запись в середине пакета — нет). В сомнениях оборачивайте в `tokio::pin!` и проверяйте poll руками.

### 56. Дроп `JoinHandle`

Дроп `JoinHandle` НЕ отменяет задачу — она продолжает работать в фоне, и её результат теряется. Чтобы отменить, надо явно вызвать `handle.abort()` или использовать `CancellationToken`/scope. Это ловушка для тех, кто привык к structured concurrency. Для structured-стиля смотрите `tokio::task::JoinSet` или `tokio_util::task::AbortOnDropHandle`.

### 57. Таймаут без аллокаций

`tokio::time::timeout(dur, fut)` оборачивает future, после `dur` возвращает `Err(Elapsed)`. Внутри использует `Sleep` и `select!`. Без аллокаций — если `fut` уже на стеке (например, `async` блок локально). Если нужно совсем без зависимостей tokio, можно вручную: `Pin` оба future, в цикле `poll` оба, при тайме возвращаем `Pending` и регистрируем waker. На практике никогда не пишут руками — берут готовое.

### 58. `Stream` vs `Iterator`

`Stream` — async-аналог `Iterator`: `poll_next(self: Pin<&mut Self>, cx: &mut Context) -> Poll<Option<Item>>`. `for await` не стабилизирован, потому что нужен generators feature и доработка trait-системы. Используют `while let Some(x) = stream.next().await` (требует `StreamExt` из `futures` или `tokio-stream`). `Stream` дороже по абстракции, у него нет такой богатой адаптеров стандартно — поэтому многие крейты делают `async fn next(&mut self)` на структуре вместо реализации `Stream`.

### 59. Backpressure в стримах

Производитель должен замедляться, если потребитель не успевает. Реализация: bounded `mpsc` канал. Send `.await`-ит при заполненной очереди, что создаёт обратное давление. В `futures::stream` есть `.buffered(n)` — ограничивает параллелизм. Для HTTP-серверов смотрите `tower::limit::ConcurrencyLimit`. Антипаттерн: unbounded channel — даст OOM при медленном потребителе.

### 60. `Send` `MutexGuard` через `.await`

`std::sync::MutexGuard` не `Send`, потому что на некоторых ОС unlock должен происходить в том же потоке, который lock-нул. Если держать guard через `.await` и future перешлют на другой worker, будет UB. Компилятор это ловит: `async fn foo(m: &Mutex<i32>) { let g = m.lock().unwrap(); some_await.await; }` не пройдёт `spawn` с `Send` bound. Решения: `tokio::sync::Mutex` (его guard `Send`, но lock асинхронный), либо отпустить guard до `.await` (`{ let g = m.lock(); use(g); } // drop`).

### 61. `async fn` в трейтах

До 1.75 `async fn` в трейте требовала `#[async_trait]` (макрос, который превращал её в `Box<dyn Future>`, с аллокацией на каждый вызов). С 1.75 — RPITIT (return position impl trait in trait): `async fn` в трейте работает без аллокаций, но возвращаемый future не имеет именованного типа, что мешает прокидывать его через границы `dyn`-трейтов. Для `dyn`-совместимости пока всё ещё `async_trait` или ручной `Box<dyn Future>`.

### 62. `Waker`

`Context::waker()` возвращает `&Waker` — handle, по которому future говорит executor-у «разбуди меня, когда событие произойдёт». Внутри `Waker` — пара `(data: *const (), vtable: &RawWakerVTable)`. При `wake()` вызывается соответствующий метод vtable, обычно — `Arc<TaskInner>` через клон или ссылку. Если в `poll` забыть сохранить waker (например, всегда возвращать `Pending` без регистрации) — future зависнет навсегда, executor никогда не разбудит. Также важно: при повторном `poll` нужно использовать новый `waker` из текущего `cx`, потому что старый мог устареть.

## Unsafe, FFI, низкий уровень

### 63. Что требует `unsafe`

Ровно пять операций: разыменование сырого указателя, вызов unsafe-функции (в том числе FFI), чтение/запись изменяемой статики, реализация unsafe-трейта, доступ к полям `union`. Всё остальное (`unsafe impl Sync`, например) — это про реализацию unsafe-trait. Что компилятор НЕ проверяет в unsafe-блоке: соблюдение aliasing-правил у сырых указателей, валидность invariant-ов типов (нельзя создать `bool` со значением 2), правильность `Send`/`Sync` у unsafe impl, отсутствие race-condition. Unsafe не отключает borrow checker для безопасных ссылок.

### 64. UB в Rust vs UB в C

В Rust набор UB меньше и формальнее: разыменование null/dangling, нарушение aliasing (`&mut` алиасит с другой ссылкой), невыровненный доступ, валидность типа (uninit `bool`, `enum` вне диапазона), data race, signed overflow в дебаге паникует, в release wraps — НЕ UB. В C UB сотни форм: signed overflow, strict aliasing, sequence points, returning через void. Rust в принципе зафиксировал, что UB — это не «делает что хочет», а «программа считается несуществующей». `miri` ловит почти весь Rust UB. На C полагаются на UBSan, ASan и удачу.

### 65. `*const T`, `*mut T`, `&T`, `&mut T` и aliasing

`&T` — shared, многих одновременно, нельзя писать (кроме interior mutability). `&mut T` — exclusive, никаких других ссылок на тот же объект. Эти правила должны соблюдаться даже если ссылку не используют. Сырые `*const T`/`*mut T` не имеют aliasing-правил, но в момент превращения в `&T`/`&mut T` через `unsafe { &*p }` правила снова применяются. Поэтому `let p = &mut x as *mut _; let r = &x; unsafe { *p = 5; }` — UB: пока жив `r`, нельзя писать ни через какой указатель.

### 66. Stacked borrows и tree borrows

Stacked borrows — модель, придуманная для формализации aliasing в Rust: каждая ссылка имеет тег, есть стек тегов на каждой ячейке памяти, доступ должен проходить через тег, лежащий на правильной позиции. Tree borrows — новая модель (2023), исправляет некоторые ложные срабатывания stacked borrows, особенно с `&`-ссылками внутри `UnsafeCell`. Miri поддерживает обе и проверяет их при `MIRIFLAGS=-Zmiri-tree-borrows`. На практике, если ваш unsafe-код прошёл tree borrows и stacked borrows под miri, скорее всего он soundness-OK.

### 67. `mem::transmute`

Побитовое переинтерпретирование одного типа в другой. Корректно когда: размеры совпадают (compile-time check), битовый шаблон валиден для целевого типа (`u32 -> f32` всегда ок, `u8 -> bool` только для 0/1, иначе UB). Альтернативы: `as` для числовых, `u32::from_ne_bytes` для байт-массивов, `std::mem::transmute_copy` если размеры разные (опасно), `bytemuck::cast` с runtime-проверками или compile-time bounds через `Pod`/`Zeroable` трейты. На code review каждый `transmute` требует комментария с обоснованием инвариантов.

### 68. `Vec::from_raw_parts` с чужим указателем

`Vec::from_raw_parts(ptr, len, cap)` берёт владение указателем. Vec при дропе вызовет `dealloc` через свой аллокатор с тем же `(layout, ptr)`. Если `ptr` пришёл из `malloc` (C-код), Vec позовёт Rust-аллокатор для `dealloc` — UB (на glibc может случайно работать, но это не контракт). Если `cap` не совпадает с реальной аллокацией — UB. Правило: `from_raw_parts` использовать только с указателями, полученными из `Vec::into_raw_parts` или `Box::into_raw` той же сборки. Для C-указателей оборачивайте в свой тип с `Drop`, вызывающий нужный `free`.

### 69. `Drop` для типа с сырым указателем

Стандартный паттерн (RAII-обёртка):
```rust
struct CHandle(*mut ffi::Handle);
impl Drop for CHandle {
    fn drop(&mut self) {
        if !self.0.is_null() {
            unsafe { ffi::handle_free(self.0); }
        }
    }
}
```
Тонкости: проверять null если конструктор может вернуть его; не делать `Drop` рекурсивным (если поле — это `Vec<CHandle>`, оно само дропнется); реализовать `Send`/`Sync` явно через `unsafe impl` после анализа thread-safety C-API. Если у вас self-referential данные через указатель — нужен `PhantomPinned` и `Pin`.

### 70. `ManuallyDrop`

Обёртка `ManuallyDrop<T>` отключает автоматический дроп. Применения: union-поля (компилятор не знает, какое поле активно), частичный move из структуры с `Drop` (вы хотите забрать одно поле, а остальное уронить вручную), отложенная очистка. `ManuallyDrop::take` — unsafe, забирает значение и помечает место как невалидное (нельзя пользоваться после). `ManuallyDrop::drop` — unsafe, вручную дропает. Использовать только когда обычный move не работает.

### 71. `repr(C)`, `repr(transparent)`, `repr(packed)`

`repr(C)` — раскладка как в C: поля в порядке объявления, с padding по alignment. Для FFI обязательно. По умолчанию Rust имеет право переупорядочивать поля для уплотнения. `repr(transparent)` — для однополевых структур, делает обёртку семантически идентичной полю в FFI и ABI. Так делают newtype вокруг `i32` для FFI. `repr(packed)` — выравнивание 1 (или указанное), padding нет. Используется для парсинга бинарных протоколов (заголовки PE, ELF, IP). Опасно из-за вопроса 72.

### 72. Alignment и `repr(packed)`

В `repr(packed)` структуре поле может лежать невыровненно. Взять `&field` — UB, потому что Rust ожидает выровненные ссылки. Компилятор это даже не разрешает (warn-by-default, скоро error). Доступ — только через `std::ptr::addr_of!(s.field)` для чтения через unaligned, или копирование в локальную переменную (`let v = s.field;` — компилятор сгенерит unaligned load). Для парсинга используйте `zerocopy` или `bytemuck`, они помогают делать выровненные представления.

### 73. FFI с C-библиотекой и деструктором

```rust
extern "C" {
    fn lib_create() -> *mut Handle;
    fn lib_destroy(h: *mut Handle);
}

pub struct Wrapper(NonNull<Handle>);
impl Wrapper {
    pub fn new() -> Option<Self> {
        let p = unsafe { lib_create() };
        NonNull::new(p).map(Wrapper)
    }
}
impl Drop for Wrapper {
    fn drop(&mut self) {
        unsafe { lib_destroy(self.0.as_ptr()); }
    }
}
```
Дальше реализуйте `Send`/`Sync` явно после изучения thread-safety C-кода. Для borrow-API делайте методы через `&self`/`&mut self` и пробрасывайте указатель внутрь.

### 74. `&[u8]` в `&str` через transmute

`&str` имеет инвариант: данные — валидный UTF-8. `transmute` не проверит, и любой следующий код, ожидающий UTF-8 (итерация по `chars`, индексация), словит UB. Используйте `std::str::from_utf8(&[u8]) -> Result<&str, Utf8Error>` — он проверяет валидность. Если уверены и хотите без проверки: `str::from_utf8_unchecked`, и это вы расписываетесь в обещании, что данные валидны.

### 75. Provenance и `strict_provenance`

Каждый указатель в Rust концептуально имеет provenance — «откуда он взялся». Указатель, полученный из аллокации A, не может легально обратиться к памяти аллокации B, даже если численно адреса совпадают. Это позволяет компилятору агрессивно оптимизировать. `int-to-ptr` касты (`addr as *mut T`) ломают provenance: компилятор не знает, что вы имели в виду. API `strict_provenance` вводит `ptr.addr()`, `ptr.with_addr(new_addr)`, `ptr.expose_addr()` для явной работы с этим. В рабочем коде, особенно для тегированных указателей и интрузивных структур.

### 76. Кастомный аллокатор

Реализовать трейт `GlobalAlloc` (для глобального) или `Allocator` (для контейнеров, nightly). Инварианты: `alloc(layout)` возвращает указатель выровненный по `layout.align()`, размером ≥ `layout.size()`, либо null при OOM. `dealloc` принимает указатель, полученный из `alloc` с тем же layout. Запрещено возвращать алиасинговые указатели. Должен быть `Send + Sync` для глобальной установки. Практика: `mimalloc`, `jemalloc` через `jemallocator` крейт. Для тестов `StatsAlloc` ловит утечки.

### 77. Soundness vs unsafe блок

Soundness — это свойство API: какие бы безопасные программы его ни использовали, UB не возникнет. `unsafe { }` блок — это место, где компилятор разрешает писать определённые операции. Функция, использующая `unsafe` внутри, может быть sound, если она проверяет все условия и никогда не даёт пользователю спровоцировать UB. Пример sound: `Vec::push` использует `unsafe` внутри, но снаружи безопасен. Пример unsound: `fn get(v: &[i32], i: usize) -> i32 { unsafe { *v.get_unchecked(i) } }` — sound только если документировано, что вызывающий проверяет `i`. Unsafe API должен явно описывать инварианты в `# Safety` секции.

### 78. `mem::uninitialized` и `MaybeUninit`

`mem::uninitialized<T>()` создавал значение `T` с произвольным битовым шаблоном. Для типов с валидными битовыми инвариантами (`bool`, `&T`, `enum`) — мгновенное UB. `MaybeUninit<T>` имеет тот же размер и alignment, но семантически «может быть невалидно»: компилятор не предполагает, что внутри валидный `T`. Создаётся через `MaybeUninit::uninit()`, заполняется через `.write(value)` или `.as_mut_ptr().write(...)`, после полной инициализации — `.assume_init()` (unsafe). Для частично инициализированных массивов есть `MaybeUninit::array_assume_init` на nightly.

## Производительность

### 79. Монорфизация

Для каждого конкретного `T`, с которым вызывается `fn foo<T>(...)`, компилятор генерирует отдельную копию машинного кода. Плюс: на каждой копии оптимизатор знает конкретный размер, alignment, может инлайнить. Минус: бинарник раздувается, время компиляции растёт квадратично с числом дженерик-параметров и точек вызова. Симптомы: 10 МБ бинарник для tiny CLI, `cargo build` 5 минут на маленьком проекте, потому что подключили `serde` + `reqwest` + `tokio`. Митигация: `Box<dyn Trait>` в местах, где производительность не критична; `-C codegen-units=1` для финального билда; `cargo bloat` для анализа.

### 80. `Box<dyn Trait>` ради сокращения кода

Если у вас generic-функция, вызываемая со многими типами, и performance не критична — `Box<dyn>` сократит бинарник в разы. Стандартный пример — error reporting: `Box<dyn Error>` вместо параметризации. Также в плагинных системах, реестрах handlers, тестовых mock-ах. Стоимость одного dyn-вызова — около 1-3 наносекунд, незаметно вне горячего цикла. Бинарник может ужаться в 2-5 раз.

### 81. Stack vs heap, почему `Vec` на куче

Stack — быстрая аллокация (просто инкремент SP), фиксированный размер на старте функции, освобождается автоматом. Heap — `malloc`/`free` через аллокатор, любой размер, время жизни — пока кто-то владеет. `Vec<T>` хранит на стеке три слова: ptr, len, cap. Сам массив элементов всегда на куче, потому что размер динамический. Маленькие `Vec` (пара элементов) можно держать на стеке через `smallvec::SmallVec<[T; N]>` или `tinyvec`. Это убирает аллокацию для типичного случая, оставляя fallback на heap для больших.

### 82. SSO

В C++ `std::string` хранит до ~22 символов inline, без аллокации. Rust `String` всегда выделяет на куче. Причины: `String` обещает, что `&str` указывает на стабильную область памяти, SSO ломает это при move (адрес меняется). Также `as_ptr().is_aligned()` гарантии. Для строк есть крейты `smartstring`, `compact_str`, `flexstr` — реализуют SSO с разными trade-off. `flexstr` ещё умеет shared-immutable (Arc-подобно). Используют в high-throughput кодах, где аллокации на каждое имя поля JSON-а становятся узким местом.

### 83. `#[inline]` и его варианты

По умолчанию компилятор инлайнит внутри одного crate, между crates — только generic-функции (через монорфизацию) и помеченные `#[inline]`. `#[inline]` — подсказка: «положи MIR в metadata, чтобы потребитель мог заинлайнить». `#[inline(always)]` — почти приказ, но LLVM может проигнорировать в патологических случаях. `#[inline(never)]` — запретить, например для отладки, для уменьшения бинарника, для оптимизации i-cache. Где использовать: маленькие функции-обёртки, accessor-ы — обычно `#[inline]`. Никогда не ставьте `always` без бенчмарка — кэш инструкций может пострадать.

### 84. `cargo asm` для горячего цикла

`cargo install cargo-show-asm`, потом `cargo asm --rust crate::path::function`. Смотрите: есть ли вызовы (`call`) — это плохо для маленьких функций, не заинлайнились. Есть ли bounds checks (`call panic_bounds_check`) — компилятор не доказал безопасность индексации. Используются ли SIMD-регистры (`xmm`, `ymm`, `zmm`) — векторизация прошла. Соотношение размера функции к ожиданию: 50 строк ассемблера на 5 строк Rust обычно нормально, 500 — что-то развернулось. Сравнение версий: переписали — посмотрели, стало лучше?

### 85. LTO и thin LTO

Без LTO: каждый crate оптимизируется отдельно, инлайнинг через границы только для `#[inline]`. LTO=true (fat LTO): весь бинарник оптимизируется как один модуль, медленный линк, но лучший код. ThinLTO: компромисс, оптимизация на уровне модулей с глобальной информацией. Включается в `Cargo.toml`:
```toml
[profile.release]
lto = "thin"
codegen-units = 1
```
`codegen-units = 1` гарантирует, что crate обрабатывается одним thread-ом, без internal parallelism, что улучшает inlining. Минус — компиляция дольше. Для release-билдов это нормально.

### 86. Профилирование под Linux

`perf record -g --call-graph=dwarf ./target/release/binary`, потом `perf report`. Для flamegraph — `cargo install flamegraph` (требует `perf` или `dtrace`), затем `cargo flamegraph --release`. Бывают сложности с символами: компилируйте с `debug = true` даже в release (`Cargo.toml` profile), чтобы видеть имена функций. Для tokio-кода добавьте `console-subscriber` и используйте `tokio-console` для просмотра состояния задач. Для аллокаций — `dhat`, `valgrind --tool=massif`. CPU vs аллокации часто разные узкие места, проверьте оба.

### 87. `Arc::clone` как узкое место

`Arc::clone` — атомарный инкремент счётчика. Сам по себе быстрый (1-2 нс), но в высоконагруженном коде с миллионом клонов в секунду из разных потоков counter становится hot cache line, и cores борются за него. Митигация: меньше клонировать (передавайте `&Arc<T>` где можно), использовать `triomphe::Arc` (нет weak-счётчика, меньше структура), на крайний — sharding: разделять данные так, чтобы каждый поток работал со своим `Arc`. Для read-mostly с очень редкими обновлениями — `arc-swap`.

### 88. Bounds check elimination

Компилятор автоматически удаляет `v[i]` bounds check, если может доказать, что `i < v.len()`. Помогает: `for i in 0..v.len()` (LLVM видит инвариант), assert!(i < v.len()) перед циклом (явный hint), итераторы вместо индексов (`for x in &v` — без bounds check), `v.iter().take(n)` вместо `v[..n].iter()` в неочевидных случаях. Проверить можно через cargo-asm или `cargo +nightly rustc -- --emit=llvm-ir` и поиск `panic_bounds_check`.

### 89. SIMD в Rust

`std::arch` — низкоуровневые intrinsics по архитектурам (`_mm256_add_ps`), требуют `#[target_feature(enable = "avx2")]` и `unsafe`. `std::simd` (portable, на nightly) — высокоуровневое API (`Simd<f32, 8>`), сам выбирает инструкции по архитектуре. `packed_simd2`/`wide` — старые крейты, отходят. Для большинства задач: пишите наивный цикл, проверяете cargo-asm на наличие `xmm/ymm` — если LLVM сам векторизовал, поздравляю. Если нет — анализ почему (есть ли зависимости между итерациями, есть ли bounds checks). Ручной SIMD — последняя миля для конкретного железа.

## Макросы и метапрограммирование

### 90. `macro_rules!` vs proc-macro

`macro_rules!` — декларативные, паттерн-матчинг по токенам, работают на синтаксическом уровне. Просты, не требуют отдельного crate. Ограничены: нельзя анализировать тип, нельзя генерировать сложный код. Подходят для DSL вроде `vec![1, 2, 3]`, `println!`. Proc-macro — на Rust, имеют доступ к `syn` (парсер) и `quote` (генератор). Три вида: `#[derive(MyTrait)]`, атрибутные `#[my_attr]`, function-like `my_macro!()`. Нужен отдельный crate с `proc-macro = true`. Сложнее, дольше компилируются. Используйте когда нужно осмыслить структуру (поля enum, generic-параметры).

### 91. Hygiene в макросах

Макрос «гигиеничен», если введённые им идентификаторы не путаются с пользовательскими. `macro_rules!` гигиеничен по идентификаторам, но не по типам и не по `crate`-путям (нужны `$crate::path`). Пример: `macro_rules! m { () => { let x = 1; } }`. После вызова в коде с другим `x` они разные переменные. Proc-macro по умолчанию НЕ гигиеничен — `quote!` производит токены с `Span::call_site`, которые видны как написанные пользователем. Для гигиены используют `Span::mixed_site` или явный `Ident` с правильным span-ом.

### 92. Фрагменты `expr`, `ty`, `pat`, `ident`, `tt`

В `macro_rules!` правая часть паттерна указывает, что ожидается. `$x:expr` — любое выражение, можно использовать в expression-позиции. `$t:ty` — тип, для declaration. `$p:pat` — паттерн match-arm. `$i:ident` — один идентификатор. `$tt:tt` — один token tree, самое гибкое (любая скобочная группа считается одним tt). Используется для проксирования аргументов в другие макросы. Ограничения follow-set: после `expr` нельзя `-` (двусмысленно), после `ident` можно почти всё. Правила менялись между edition-ами, в edition 2021 ужесточились для `pat`.

### 93. Derive-макрос со своим состоянием

Парсинг через `syn::DeriveInput`, генерация через `quote!`. Каркас:
```rust
#[proc_macro_derive(MyTrait, attributes(my_attr))]
pub fn derive_my_trait(input: TokenStream) -> TokenStream {
    let input = parse_macro_input!(input as DeriveInput);
    let name = input.ident;
    let expanded = quote! {
        impl MyTrait for #name {
            fn method(&self) -> usize { 42 }
        }
    };
    expanded.into()
}
```
Для атрибутов парсите `input.attrs` и фильтруйте по `attr.path().is_ident("my_attr")`. Для generic-структур не забывайте прокидывать `impl_generics`, `ty_generics`, `where_clause`. Тестировать через `trybuild` для compile-fail кейсов и `macrotest` для snapshot-сравнения.

### 94. `syn`, `quote`, `proc-macro2`

`proc_macro` (без двойки) — встроенный crate, доступен только в proc-macro crate-ах. Его типы не `Send`, нельзя использовать вне процедурного контекста. `proc-macro2` — обёртка с тем же API, но доступна везде и тестируется в unit-тестах. `syn` — парсер Rust-кода в AST. `quote` — генератор кода через интерполяцию. Стандартный стек proc-макроса: парсим `proc_macro::TokenStream` через `syn`, генерируем `proc_macro2::TokenStream` через `quote`, на выходе `.into()` обратно в `proc_macro::TokenStream`.

### 95. Атрибутные макросы vs derive

Derive получает только `DeriveInput` (struct/enum/union), не модифицирует исходный код, только добавляет новый. Атрибутный получает любой item (`#[my_attr] fn foo() { ... }`) и может полностью переписать. Соответственно атрибутный мощнее, но ломает rust-analyzer (IDE не понимает, что внутри). Derive — для импла трейтов. Атрибут — для трансформации (`#[tokio::main]`, `#[derive(serde::Serialize)]` это derive, а `#[serde(rename = "x")]` — helper attribute которое использует только сам serde derive).

## Архитектура и дизайн API

### 96. Typestate pattern vs runtime-проверки

Typestate кодирует состояние в типе: `Connection<Disconnected>`, `Connection<Connected>`. Методы доступны только в нужном состоянии. `fn send(self: Connection<Connected>, msg: Msg)` — нельзя послать через disconnected. Плюсы: ошибки на этапе компиляции, нулевая стоимость в runtime, API самодокументирующийся. Минусы: больше типов, сложнее хранить в коллекциях (нужна enum-обёртка), плохо для динамических переходов. Используйте для критичных протоколов (TLS handshake, builder с required-полями), не используйте для типичных «is_loaded: bool» в DTO.

### 97. Builder pattern

Два варианта: by-reference (`fn name(&mut self, x: T) -> &mut Self`) — удобно для опциональных, можно сохранять промежуточные builder. By-value consuming (`fn name(mut self, x: T) -> Self`) — позволяет менять тип self (typestate-builder), но не сохранить промежуточный. Для required-полей: typestate builder, где каждый `with_field` переключает в новое состояние. На крейтах: `derive_builder` для простых случаев, `bon` (новее) для type-state, `typed-builder` для compile-time проверки полноты.

### 98. Не-breaking добавление поля

Сделайте структуру `#[non_exhaustive]`. Тогда пользователи не смогут конструировать через struct literal `{ ... }` и не смогут exhaustively pattern-match без `..`. После этого добавление поля — не breaking. Альтернатива: builder + приватный конструктор. Для возвращаемых структур (например, `Config`) обычно делают `Config::builder()` или `Config::default()` + сеттеры. На `enum`-ах тоже работает `#[non_exhaustive]`, что позволяет добавлять варианты. Помните: `#[non_exhaustive]` влияет только на cross-crate использование, внутри своего crate-а вы всё ещё можете конструировать напрямую.

### 99. Sealed trait

Цель: чтобы внешние crate-ы не могли реализовать ваш трейт, только вы сами. Идиома:
```rust
mod sealed { pub trait Sealed {} }
pub trait MyTrait: sealed::Sealed { ... }
```
Реализуете `Sealed` только для своих типов. Внешние crate-ы не имеют доступа к `sealed::Sealed` (приватный модуль), поэтому не могут добавить `impl MyTrait for Foo` — компилятор потребует `Sealed`, которого они не могут реализовать. Применения: вы хотите добавлять методы в трейт без breaking change (если третий мог реализовать, ваше добавление сломает его). Используют `std` (`OsStrExt` и т.п.).

### 100. Ошибки в библиотеке: `thiserror`, `anyhow`, custom enum

`thiserror` — derive-макрос для библиотечных ошибок. Генерирует `Display`, `Error`, `From` для конверсий. Получаете типизированный enum, пользователь может matchать конкретные варианты.

```rust
#[derive(thiserror::Error, Debug)]
pub enum MyError {
    #[error("io error: {0}")]
    Io(#[from] std::io::Error),
    #[error("parse error at line {line}")]
    Parse { line: usize },
}
```

`anyhow` — для приложений: `anyhow::Error` это `Box<dyn Error + Send + Sync + 'static>` с контекстом. Прекрасно для main, скриптов, везде, где не нужно различать варианты. `anyhow::Result<T>` упрощает `?` без определения собственных типов.

Custom enum без derive — когда нужно очень специфичное поведение (например, конверсии через серверный response), но в 95% случаев `thiserror` достаточно. Для библиотеки используйте `thiserror`, для приложения — `anyhow`. Смешивать можно: библиотека отдаёт `thiserror`-тип, приложение оборачивает в `anyhow` с контекстом через `.context("loading config")`.
